# 回执缺失与性能瓶颈诊断

本次只定位原因，正式服务源码和基线二进制未改变。使用独立库 `tokmall_bench_1791717447`、Redis DB14；诊断二进制通过Go build overlay增加127.0.0.1:19092上的pprof和投递ID日志。数据库活动每200ms采样、计数每约1秒采样，CPU/block/mutex各取15秒窗口。这些实验含观测开销、只做单轮定位，不能替换正式容量基线。

## 1. 回执缺失：未消费消息被长度裁剪删除

50并发、单热点SKU、60秒、同样的交易与归因逻辑：

| 诊断档 | 完整订单/秒 | 支付订单 | 回执/投影缺口 | Stream最终条数 | DLQ |
|---|---:|---:|---:|---:|---:|
| 默认MAXLEN约10,000，首次复现 | 373.5 | 22,448 | 10,668 | 10,002 | 0 |
| 默认MAXLEN约10,000，完整ID追踪 | 389.1 | 23,386 | 11,653 | 10,004 | 0 |
| 仅将诊断保留上限改为1,000,000 | 392.4 | 23,581 | 0 | 23,581 | 0 |

三档HTTP请求全部成功，库存/支付事实正确。默认裁剪完整追踪档的23,386个事件全部取得成功XADD返回的Stream ID。缺失的11,653个事件全部满足：成功投递、Stream ID早于最终第一条保留消息 `1791717712573-1`、不在保留集合、没有回执/投影、DLQ为空；服务日志无消费失败、解码失败或未订阅类型警告。发布标记不是消费确认，[transport.go](../../../internal/outbox/transport.go)中的 `XADD MAXLEN ~` 没有保护未消费/未确认消息，因此完成投递后依然可能被裁掉。

可以离线核对 `commerce-c50-trim10k-r2/publish-identities.json.gz`、`missing-events.json`、`retained-identities.json`和`trim-proof.json`；后者记录匹配数与示例。最终消费组pending=0、lag=0，不能说明历史业务事件都已消费。裁掉的事件不再能由正常新消息读取恢复，必须依靠PG事实和对账重放。

默认裁剪追踪档10～50秒采样窗口：发布约391.8事件/秒，回执约26.9事件/秒；未写回执的已发布事件最多21,517个，超过保留上限。提高上限后，负载结束并等待普通消费可得到全部23,581个回执，九项对账通过，未人工重放。这是根因对照，**不是修复**：持续负载下积压仍会增长，任意固定上限都可能再次裁掉未消费消息。

## 2. 热点交易：库存行锁拖住共享连接池，消费受到挤压

PostgreSQL采样的所有Lock等待都指向同一SKU的 `UPDATE inventory SET quantity=quantity-$1...`，首档共5,419个这样的活动采样记录，主要为transactionid/tuple等待。Go阻塞剖析15秒窗口中，`database/sql.(*DB).conn`累计410.12秒，占总goroutine阻塞时间49.02%；这是累计阻塞时间，不能解读为49%的CPU或单请求延迟。

库存余额必须串行更新，当前行锁一直保持到库存流水、订单项、超时事件和事务提交完成；锁后仍有多次数据库往返。大量下单事务等待这行锁时仍占用连接，25个连接的同一池还供支付、中继、消费者和其他worker使用。消费者每批读取32条，却逐条开始事务、写回执/投影并提交；在本轮压力下，消费速度被压到发布速度以下。读取批量32不等于批量事务处理。

改动方向应是缩短库存持锁时间、减少事务内往返，并给后台消费明确的连接预算及吞吐目标。增大池可能只是让更多事务在数据库里等待同一行，不能据此认定交易吞吐提高；不能去掉事务、库存约束或幂等来换性能。

## 3. Feed：每请求动态装配的数据库通路限制吞吐

保持100并发、30秒、相同固定首页与诊断观测：

| 诊断变体 | 请求/秒 | P99 ms | 说明 |
|---|---:|---:|---|
| 25连接、默认日志和并行度 | 7,389.8 | 36.12 | 每请求查询点赞及商品卡 |
| 仅提高到50连接 | 7,335.4 | 29.46 | 等待减轻，吞吐未提高 |
| 仅降低成功日志量（WARN级别） | 7,513.7 | 35.83 | 变化小，不能证明容量收益 |
| 仅设置API GOMAXPROCS=8 | 7,708.2 | 34.72 | 单轮变化不足以证明新优化收益 |
| 固定首页预加载点赞和商品卡 | 25,251.7 | 16.63 | 诊断消融，不能作为已交付优化成绩 |

标准诊断档阻塞剖析中，获取DB连接累计占87.97%的goroutine阻塞时间：`fillLikeCounts`路径44.21%，`fillProductCards`路径43.76%。两条动态读取每个请求都执行，Feed主体命中L1仍然需要这两次往返。25→50连接使池累计等待约2,155.6→1,384.9秒，但吞吐没有提高，说明加池主要重新分配等待，不能消除动态查询链路的成本。

代表性EXPLAIN ANALYZE的执行时间：点赞0.095ms、商品卡0.153ms，没有百万视频全表扫描；这不包含客户端排队、驱动和网络往返，也不代表其他数据密度下的SQL成本。本次点赞数据稀疏，首页商品卡只有测试挂载关系。CPU剖析中slog.InfoContext访问日志路径约18.8%，JSON编解码路径各不足1%；剖析比例不直接等于能移除的请求耗时，日志对照也未显示显著吞吐收益。

预加载变体仍用原查询取得固定20个视频对应的点赞和商品卡，再在只读测试窗口复用；期间没有点赞、商品或关系写入。它去掉每请求动态SQL，观察到约3.4倍吞吐，支持该通路是当前首页吞吐的主要限制。它不支持不同ID集合和写后更新，**不得上线或宣称生产缓存优化已完成**。实际优化需要保留上下架/解绑可见性、定义缓存失效与陈旧窗口，并用相同业务语义重测。

## 证据与边界

各档summary、Prometheus快照、PG活动记录、pprof、goroutine栈和对账见子目录；`aggregate.json`为诊断汇总，代表性执行计划位于根目录。`diagnostic-tools.tar.gz`包含实际runner、overlay和观察器源码；环境文件记录诊断二进制SHA256。完整服务日志、Stream载荷及逐请求k6数据留在本机 `.gocache/diagnostics/2026-10-11/results/`，清理缓存前应备份。

首档取样成功但协调器日志拷贝因局部import遮蔽失败，完整ID证据通过修正后的第二档补齐；首档不用于发布ID证明。诊断API、观察器和剖析监听均已停止，测试资源保留供核验。新建的诊断库与Redis DB14和原基线库/DB15独立，没有修改业务库或正式实现。

额外代码发现：[FetchPending](../../../internal/outbox/repository.go)写入leased_until，却没有在取件条件中过滤未到期租约，多中继可能重复认领。单实例完整追踪没有重复发布，这不是本次裁剪缺口的原因，但在多实例验证前应单独修正。
