# 内容电商后端与 Agent 项目作战手册

## 0. 项目定位

项目名称：`Content Commerce Platform`

目标：用一个持续演进的项目，展示 Go 后端、CloudWeGo、高并发交易、异步架构、可观测性和 Agent 工具调用能力。项目用于求职演示和面试讨论，不以生产级规模为目标。

核心用户链路：

1. 用户浏览视频 Feed，并产生点赞、关注、播放等行为。
2. 用户在活动期间购买限量商品，系统保证不超卖、不重复下单。
3. 用户向 AI 客服咨询商品、订单和售后，Agent 通过受控业务工具完成处理。

## 1. 范围控制

### 版本拆分

不要把三大能力定义为同一个 v1。每个阶段都必须能独立运行、演示和复盘：

- **Feed v1**：登录、视频元数据、对象存储、时间排序 Feed、点赞/关注、播放事件。
- **Commerce v1**：商品、SKU、库存、订单、模拟支付、单商品秒杀。
- **Agent v1**：商品查询、订单查询、售后规则、转人工和工具调用审计。

公共基础设施可以逐步引入：Feed 先用 PostgreSQL + Redis + MinIO；Commerce 再引入 Kafka；Agent 最后接入向量检索和 LLM。不要为了“完整技术栈”提前部署所有中间件。

### 第二版再做

- 关注 Feed 和热门排序
- 搜索（OpenSearch）
- 行为分析（ClickHouse）
- Outbox 事件投递
- 独立 Feed、Commerce、Agent 服务
- Kitex RPC、服务发现、限流和降级
- Prometheus、Grafana、OpenTelemetry、Jaeger/Tempo

### 明确不做

- 真正的视频转码和 CDN 优化
- 复杂推荐模型
- 真实支付清结算
- 多仓库、多币种、复杂优惠券
- 一开始就拆成十几个微服务
- 无法解释的多 Agent 自主协作

任何新想法先记录到 `later.md`，不在当前迭代直接实现。

## 2. 推荐技术栈与选型口径

### 技术栈

- Go：业务服务、Worker、Agent Gateway
- Hertz：HTTP 接入层
- Kitex：服务拆分后的内部 RPC
- Thrift 或 Protobuf：统一 IDL，二选一并贯彻
- PostgreSQL：业务事实数据和事务
- Redis：缓存、限流、库存预扣、短期会话
- Kafka：领域事件和异步削峰
- MinIO：视频和图片对象存储
- OpenSearch：商品/视频搜索（第二阶段）
- ClickHouse：行为与漏斗分析（第二阶段）
- Prometheus + OpenTelemetry：指标和链路
- Docker Compose、Kubernetes、GitHub Actions
- k6：压测；Testcontainers：集成测试

### Hertz 为什么不是“为了用而用”

普通 CRUD 使用 Gin 完全合理。选择 Hertz 的依据是：项目需要高并发接口压测、希望使用 CloudWeGo 生态中的代码生成和治理能力，并计划与 Kitex 形成一致的服务体系。代价是生态和资料相对小，必须通过业务层封装降低框架耦合。项目中记录 Gin/Hertz 的性能、开发效率和依赖成本对比。

### Kitex 何时引入

第一版用模块化单体，Hertz 直接调用内部 service。只有当 Feed、Commerce、Agent 存在独立扩缩容、故障隔离或团队边界时，才拆成 Kitex 服务。面试时说明：拆分由边界和运行特征驱动，而不是为了展示微服务。

## 3. 目标架构

第一阶段：

```text
Client -> Hertz API -> module service -> PostgreSQL/Redis
                              -> Kafka -> Worker
Video files -----------------> MinIO
```

第二阶段：

```text
Client -> Hertz Gateway
            |-> Kitex Feed Service
            |-> Kitex Commerce Service
            |-> Kitex Agent Service
            |-> Search/Analytics
```

推荐目录：

```text
cmd/api/                 HTTP API
cmd/worker/              Kafka consumers and jobs
internal/user/
internal/video/
internal/feed/
internal/product/
internal/inventory/
internal/order/
internal/customer_service/
internal/agent/
internal/event/
internal/observability/
```

模块约束：`handler` 只处理协议，`service` 处理业务规则，`repository` 访问数据库，`event` 发布事件，`worker` 执行异步任务。

## 4. 16 周交付路线

### 第 1 周：工程基线

交付：仓库、README、配置、日志、统一错误、请求 ID、健康检查、数据库迁移、Docker Compose、CI、OpenAPI。

完成定义：新机器可以按 README 在 10 分钟内启动；至少有一个健康检查和一个集成测试。

### 第 2-4 周：视频与 Feed

交付：视频元数据、MinIO 上传、游标分页、点赞/关注、播放事件、Redis 热点缓存。

演进顺序：时间排序 -> 关注 Feed -> 热门分数 -> 简单召回/排序。

验收：分页不重复；缓存命中率可观测；播放事件不会阻塞 Feed 响应；有 k6 基线。

### 第 5-7 周：商城与订单

交付：商品、SKU、库存、订单状态机、模拟支付、幂等请求、订单超时关闭。

验收：重复请求只产生一个订单；非法状态转换被拒绝；数据库事务边界有文档和测试。

### 第 8-9 周：秒杀

流程：限流 -> 鉴权 -> Redis Lua 原子预扣 -> Kafka 排队 -> Worker 创建订单 -> 数据库确认。

必须测试：超卖、重复下单、消息重复消费、消息积压、Redis 成功但投递失败、订单超时回补、数据库失败。

验收：在固定压测场景下无超卖；记录 QPS、P95/P99、成功率、排队时间和库存差异。

### 第 10-11 周：AI 客服

工具：`search_products`、`get_order_status`、`get_return_policy`、`create_after_sale`、`transfer_to_human`。

必须实现：结构化输出、工具参数校验、资源权限校验、超时、重试、降级、敏感操作二次确认、会话审计、Token/延迟统计。

验收：固定评测集能重跑；工具调用准确率、回答正确率、失败率和成本可统计；Agent 不能直接执行任意 SQL。

### 第 12-14 周：消息、搜索、分析、观测

交付：Kafka 领域事件、Outbox（可选但推荐）、OpenSearch、ClickHouse、Prometheus、Grafana、OpenTelemetry。

验收：一次请求能看到跨 HTTP、Redis、数据库和 Kafka 的 Trace；关键业务有 Dashboard 和告警阈值。

### 第 15-16 周：拆分、故障和求职材料

交付：按真实边界拆出至少一个 Kitex 服务；Docker/Kubernetes 部署；故障演练；架构图、压测报告、ADR、简历项目描述、演示脚本。

## 5. 数据与一致性原则

- PostgreSQL 是订单、库存和支付状态的事实来源。
- Redis 适合快速判断和削峰，不能单独作为最终订单事实。
- 所有消费端必须幂等，使用业务唯一键或幂等表。
- 跨数据库和 Kafka 的可靠发布使用 Outbox 或明确的补偿机制。
- 每个状态机都定义合法转换和不可逆操作。
- 每个外部调用都设置超时、重试上限和降级行为。

## 6. 每个功能的开发模板

开发前写：目标、输入、输出、不做什么、完成标准。

开发中保留：接口文档、数据模型、错误码、日志字段、关键测试。

开发后验证：正常路径、边界路径、重复请求、依赖失败、压测数据。

每完成 2-3 个功能，固定安排一次整理：拆职责、删除重复、补测试、更新文档。不要把重构全部推迟到项目末尾。

## 7. 面试准备清单

每个模块准备一页 ADR，回答：问题是什么、候选方案、为什么选择、代价、失败场景、验证方法、流量扩大十倍怎么办。

重点问题：

- 为什么 Feed 使用游标分页？
- 推模式和拉模式如何取舍？
- Redis 扣库存成功但 Kafka 发送失败怎么办？
- 如何防止消息重复消费和重复下单？
- Redis、数据库、Kafka 分别故障时系统如何降级？
- 哪些模块值得拆成 Kitex 服务？
- Agent 如何防越权、重复退款和 Prompt Injection？
- 如何评估 Agent 是否真的变好？
- P99 延迟升高时如何定位？
- Gin 与 Hertz 的收益和代价是什么？

推荐回答框架：先说约束，再说方案，再说代价，最后说验证数据。不要只报技术名词。

## 8. 防止再次烂尾

使用三类分支：`main` 始终可运行，`feature/*` 只做一个小功能，`refactor/*` 只整理不加功能。每个阶段最多保留 3 个进行中的任务。

出现“改哪里都害怕”时，暂停加功能，先画依赖图、补一个端到端测试、拆出最混乱的职责。想推倒重来时先创建归档分支并写复盘，不删除项目。

每周复盘四项：本周可演示成果、最大复杂度来源、下周唯一重点、暂时明确不做的事情。

## 10. Feed v1 详细拆解

Feed v1 只做时间排序和关注关系，不做复杂推荐模型。先把“稳定返回一页内容”做正确，再逐步演进排序。

### 10.1 核心数据

| 表 | 说明 | 完整 DDL 见 |
|---|---|---|
| `users` | 用户和状态（含 email/username/password_hash/role/status） | supplement §3.1 |
| `videos` | 作者、对象存储 key、封面、状态、发布时间、统计计数 | supplement §3.2 |
| `follows` | 关注关系，含 `CK_FOLLOW_NO_SELF` 和关注上限 1000 | supplement §3.3 |
| `likes` | 点赞关系，唯一键为 `(user_id, video_id)` | supplement §3.4 |
| `play_events` | 播放事件，异步写入，`event_id` UUID 幂等 | supplement §3.5 |
| `feed_cursors`（可选） | 保存特殊场景的分页快照 | supplement §3.6 |

视频状态至少包括 `uploading`、`published`、`blocked`、`deleted`。Feed 只能返回 `published` 内容。

> **补充参考**：完整的 API 路由表、认证方案（JWT V1 → Session V2）、MinIO 上传时序、错误码、缓存 Key 规范和关键 ADR 请见 [`feed-system-supplement.md`](./feed-system-supplement.md)。

### 10.2 生产级问题、原因和方案

| 问题 | 原因 | 解决方法 | 验证方式 |
|---|---|---|---|
| 深分页越来越慢 | `OFFSET` 需要扫描并丢弃前面记录 | 使用 `(created_at, id)` 游标，按复合索引查询 | 生成百万数据比较 P99 |
| 翻页重复或漏数据 | 翻页期间有新视频插入，排序键不稳定 | 游标携带时间和 ID；固定排序规则；定义一致性语义 | 并发插入时连续翻页检查集合 |
| 热门作者导致热点 | 大量请求集中访问同一作者或视频 | 多级缓存、随机过期、热点 key 拆分、限流 | 人工制造热点 key 压测 |
| 缓存击穿 | 热点 key 同时过期 | singleflight/互斥重建、逻辑过期、预热 | 同时发起大量 miss 请求 |
| 缓存雪崩 | 大量 key 同时过期或 Redis 故障 | TTL 加随机抖动、分批预热、降级数据库、熔断 | 停 Redis，观察降级和恢复 |
| 缓存与数据库不一致 | 写库与删缓存不是原子操作 | 先写库再删缓存；必要时延迟双删；接受短暂最终一致 | 并发读写和故障注入 |
| 关注 Feed 写扩散过大 | 大 V 的新视频要写入数百万收件箱 | 普通用户推模式，小量粉丝拉模式；按用户分层 | 比较不同粉丝规模的写放大 |
| Feed 读扩散过慢 | 每次请求实时合并关注作者内容 | 预计算候选集、分页拉取、批量查询和缓存 | 关注数增长时压测读取 |
| 内容被删除仍出现在 Feed | 删除和缓存/异步索引存在延迟 | 查询时过滤状态；删除事件清理缓存和索引 | 删除后立即请求多个入口 |
| 重复视频 | 多个候选源合并或分页边界重叠 | 在请求内按 video ID 去重，并保留游标推进 | 多源合并测试 |
| 内容审核状态延迟 | 视频先发布后审核，异步状态更新 | 默认不可见；审核通过后发布；事件驱动更新 | 审核失败/超时场景 |
| 上传中断或孤儿文件 | 客户端上传成功前断开 | 分片/预签名上传、状态机、定期清理任务 | 中断上传并运行清理 |
| 播放事件拖慢接口 | 同步写每次播放 | Kafka 异步事件，批量落库；允许统计延迟 | 对比同步和异步 P99 |
| 计数不准确 | 点赞/播放事件重复、乱序或丢失 | 事件 ID 幂等；计数异步聚合；原始事件可重放 | 重复和乱序事件回放 |
| 隐私越权 | 私密、封禁或未成年内容被错误返回 | Feed 查询统一经过可见性策略；作者和观众权限校验 | 构造跨用户访问用例 |
| 冷启动无内容 | 新用户没有行为，作者无粉丝 | 热门/新内容兜底；按地域或类别初始化 | 新账号端到端测试 |
| 排序无法解释 | 分数由多个因素组成但没有记录 | 返回 rank reason 或记录排序版本和特征 | 同一输入重放结果 |

### 10.3 Feed 演进路线

1. 时间排序：数据库复合索引 + 游标。
2. 关注 Feed：先拉取关注作者最近内容，批量合并。
3. 热门 Feed：播放、点赞、完成率的简单分数，定时计算。
4. 混合 Feed：关注内容、热门内容和新内容按比例召回。
5. 生产化讨论：大 V 推拉混合、候选集缓存、排序版本、实验分流。

Feed v1 的完成标准：分页稳定、内容可见性正确、缓存有命中率指标、播放事件异步化、删除和封禁可在合理时间内生效，并有一份压测报告。

## 11. Commerce v1 详细拆解

先完成普通订单，再加入秒杀。库存不是唯一风险，交易系统的核心是状态、幂等和补偿。

### 11.1 订单状态机

```text
CREATED -> PENDING_PAYMENT -> PAID -> FULFILLING -> COMPLETED
    |             |             |
    +-> CANCELED  +-> EXPIRED   +-> REFUNDING -> REFUNDED
```

每次状态变化必须带版本或条件更新，例如 `UPDATE ... WHERE status = ?`，防止并发请求覆盖状态。

### 11.2 交易问题、原因和方案

| 问题 | 原因 | 解决方法 | 验证方式 |
|---|---|---|---|
| 超卖 | 并发扣库存缺少原子性 | 数据库条件更新或 Redis Lua 预扣 + DB 最终确认 | 并发购买，检查库存与订单数 |
| 少卖 | 预扣成功后消息丢失或订单失败 | Outbox、补偿扫描、超时回补 | 模拟 Worker 崩溃和消息丢失 |
| 重复下单 | 客户端重试、消息重复 | 请求幂等键 + 用户/活动/商品唯一约束 | 重复 HTTP 和重复消息 |
| 重复扣库存 | 重试逻辑不幂等 | 库存流水唯一业务号，状态机控制 | 重放同一个库存事件 |
| 库存预扣后不支付 | 用户占库存不释放 | 订单超时任务、延迟消息、补偿扫描 | 快进时间测试过期订单 |
| 支付回调乱序 | 回调重复或先到取消消息 | 只允许合法状态转换；回调按支付单号幂等 | 乱序回调回放 |
| 金额被篡改 | 客户端提交价格 | 服务端重新读取商品快照并计算金额 | 修改请求价格测试 |
| 商品被下架仍能下单 | 读缓存旧数据 | 下单时再次校验商品状态和活动时间 | 下架与下单并发 |
| 秒杀流量打垮数据库 | 请求直接落库 | 网关限流、资格校验、Redis 预扣、Kafka 削峰 | 逐步增加并发观察数据库 |
| 队列积压 | 消费速度小于生产速度 | 监控 lag、扩容消费者、超时提示、拒绝过期请求 | 人工降低消费者速度 |
| 消息重复或乱序 | 至少一次投递 | 消费幂等；按订单/库存 key 分区；不依赖全局顺序 | 重复和乱序消息 |
| Redis 与 DB 不一致 | 预扣和最终确认分离 | 记录库存流水、定期对账、补偿任务 | 篡改一条记录后运行对账 |
| 热点商品 key | 所有请求访问同一个库存 key | 本地短缓存、分片 key、限流；注意分片扣减复杂度 | 单商品极限压测 |
| 恶意刷单 | 脚本重复请求 | 用户/设备/IP 限流、验证码或资格令牌、风控记录 | 模拟异常请求 |
| 订单查询读到旧状态 | 读写分离或缓存延迟 | 关键写后短时间读主库；状态事件更新缓存 | 支付后立即查询 |
| 故障后无法判断结果 | 客户端超时但服务端已成功 | 幂等查询接口和订单结果查询，不让客户端盲目重试 | 注入网络超时 |

### 11.3 秒杀的两种方案要能比较

- **数据库条件扣减**：实现简单、一致性直观；高并发下数据库成为瓶颈。
- **Redis 预扣 + 消息队列**：削峰效果好；需要处理少卖、消息失败、对账和补偿。

项目实现第二种，但保留第一种作为对照实验。面试时重点讲清楚“最终一致性如何收敛”，不要只说“用了 Redis 所以不会超卖”。

Commerce v1 的完成标准：状态机完整、请求和消费幂等、超卖与少卖都有测试、订单超时可回补、压测中有可重复的库存对账结果。

## 12. Agent v1 详细拆解

Agent 只服务于电商客服，不做开放式万能助手。先做可靠的工具调用，再考虑多轮规划。

### 12.1 Agent 风险与方案

| 问题 | 解决方法 |
|---|---|
| 模型幻觉 | 业务事实必须来自工具；结构化输出；无法确认时明确转人工 |
| Prompt Injection | 工具权限与系统规则在服务端执行；不信任检索文本中的指令 |
| 越权查询订单 | 工具层根据登录用户校验订单归属，不接受模型自行声明的身份 |
| 重复退款/售后 | 幂等键、二次确认、业务状态机 |
| 上下文过长 | 摘要、窗口化历史、检索相关上下文 |
| 延迟过高 | 流式输出、并行只读工具、超时和模型降级 |
| 模型不可用 | 重试上限、备用模型、FAQ 静态兜底、转人工 |
| 成本失控 | Token 预算、模型路由、按会话统计成本 |
| 工具返回脏数据 | 工具 schema 校验、脱敏、错误码标准化 |
| 无法评估质量 | 固定评测集、工具调用准确率、事实正确率、转人工率 |
| 敏感信息泄露 | 日志脱敏、最小权限、审计记录、输出过滤 |

Agent v1 的完成标准：每个工具有权限、超时和幂等定义；固定问题集可以回归；所有业务动作能追踪到用户、会话和工具调用。

## 13. 版本间的技术引入顺序

```text
Feed v1:
Hertz + PostgreSQL + Redis + MinIO + 基础观测

Commerce v1:
复用以上组件 + Kafka + Worker + 幂等/补偿

Agent v1:
复用业务 API + LLM + 工具层 + 会话库 + RAG/评测

演进版:
Kitex + IDL + OpenSearch + ClickHouse + Kubernetes
```

这样每次增加技术都有对应业务压力：Feed 需要缓存和事件，秒杀需要削峰和补偿，Agent 需要工具治理和评测，Kitex 则由服务拆分需求触发。

## 14. 如何合并成一个大项目：内容电商平台

三个模块通过业务链路连接，而不是共享所有内部代码：

```text
店铺/商家创建商品
        |
        v
商家发布视频 -----> 视频详情页挂载商品卡
        |                         |
        v                         v
用户浏览/点击 -------> 商品详情/秒杀活动
                                  |
                                  v
                              下单支付
                                  |
                                  v
                    AI 客服查询商品、订单、售后
```

### 14.1 统一产品定位

产品名称可以叫“短视频内容电商平台”或“内容电商交易系统”。核心角色：

- 普通用户：浏览视频、点击商品、下单、咨询客服
- 商家：创建店铺和商品、发布带商品的视频、查看订单
- 平台运营：审核内容、创建活动、处理售后

演示时不要展示三个互不相关的 Demo，而是展示一条闭环：

1. 商家创建一个商品和一个秒杀活动。
2. 商家发布一个带商品链接的视频。
3. 用户从 Feed 看到视频并点击商品卡。
4. 用户进入商品页并参加秒杀。
5. 用户打开 AI 客服询问订单状态或退款规则。
6. 后台查看播放、点击、下单和转化事件。

### 14.2 最小领域模型

建议先使用明确的 ID 引用连接领域，不要让模块直接读取彼此的数据库表：

- `shop`：`shop_id`, `owner_id`, `status`
- `product`：`product_id`, `shop_id`, `title`, `status`
- `sku`：`sku_id`, `product_id`, `price`
- `video`：`video_id`, `author_id`, `status`
- `video_product`：`video_id`, `product_id`, `position`
- `campaign`：`campaign_id`, `sku_id`, `start_at`, `end_at`, `stock`
- `click_event`：`event_id`, `user_id`, `video_id`, `product_id`, `request_id`
- `order`：`order_id`, `user_id`, `shop_id`, `source_video_id`, `status`

`video_product` 是最重要的连接表，它支持一个视频挂一个或多个商品，也允许商品下架后视频仍然存在但商品卡显示不可购买。

`orders.source_video_id` 用于最简单的内容归因。后续需要更精确时，再引入短期 attribution token，而不是一开始设计复杂的营销归因系统。

### 14.3 三阶段如何逐步接入

#### Feed v1：先做“可挂商品”的内容系统

Feed 阶段可以先不实现真实下单，但数据模型预留商品关联：

- 发布视频时可选择商品
- 视频详情返回商品卡的基本信息
- 点击商品卡记录 `click_event`
- 商品卡暂时跳转到一个静态商品详情页

这样 Feed 可以独立压测和复盘，同时已经具备未来连接商城的接口。

#### Commerce v1：把商品卡接到真实交易

商城阶段实现：

- 商品详情页
- 普通下单
- 秒杀活动
- 从 `source_video_id` 记录订单来源
- 点击到下单的转化查询

Feed 不需要知道库存扣减细节，只负责返回 `product_id` 和跳转入口。Commerce 也不需要依赖 Feed 的内部表，只接收可选的来源视频 ID。

#### Agent v1：让客服理解完整业务上下文

客服可以通过工具查询：

- 商品是否可售
- 商品来自哪个店铺
- 用户订单和订单来源视频
- 秒杀订单当前状态
- 售后规则和处理进度

Agent 不直接查询 Feed 或 Commerce 数据库，而是调用各自提供的业务 API/Kitex 接口。这样未来拆服务时，工具层不需要重写。

### 14.4 统一事件模型

模块之间通过事件提供统计和异步能力：

```text
VideoPublished
VideoViewed
ProductClicked
OrderCreated
InventoryReserved
PaymentSucceeded
OrderExpired
AfterSaleCreated
```

事件公共字段建议包括：`event_id`, `event_type`, `occurred_at`, `user_id`, `trace_id`, `version`, `payload`。消费者必须按 `event_id` 幂等。

事件用途：

- Feed：播放、点赞、关注
- Commerce：下单、支付、库存和订单超时
- Analytics：点击到下单的漏斗
- Agent：订单状态变化和客服上下文

不要让 Analytics 反过来决定交易是否成功；统计是事件消费者，订单事实仍以 Commerce 数据库为准。

### 14.5 推荐的仓库边界

初期仍是模块化单体，但模块只能通过接口通信：

```text
internal/
  content/       视频、关注、点赞
  commerce/      店铺、商品、库存、订单
  customer/      会话和客服
  integration/   领域事件和跨模块适配
```

当出现以下条件之一，再拆 Kitex 服务：

- Feed 读流量与 Commerce 写流量需要独立扩容
- Agent 的模型调用延迟影响主 API
- 某个模块需要独立发布或故障隔离
- 团队协作边界已经形成

拆分后仍保留同样的业务接口：`GetProductBrief`、`GetOrderStatus`、`RecordProductClick`。模块化单体阶段写好的接口就是未来 RPC 的候选契约。

### 14.6 一次完整演示需要准备的数据

- 一个商家和一个店铺
- 两个商品，其中一个参与秒杀
- 三条视频，其中两条挂载商品
- 一个普通用户和一个客服用户
- 一组可重复执行的秒杀库存
- 一组客服评测问题

演示脚本要能从“发布视频”走到“客服查询订单”，并在后台展示事件链路和关键指标。这样面试官看到的是一个统一产品，同时你仍然可以分别压测 Feed、秒杀和 Agent，分别复盘各自的工程问题。
