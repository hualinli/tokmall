# 性能证据与复测要求

> 更新日期：2026-10-09。当前版本全局Feed缓存对照与交易中止/恢复证据见本文末尾；历史数字保留原测量条件。旧命令、临时5433容器和丢失的`/tmp`脚本已从运行指南移除；原文可从Git历史查看。

## 证据等级与适用范围

旧记录未为每次实验保存提交SHA、容器资源上限与完整原始输出，部分机器信息还不一致：早期写Apple Silicon，Commerce段写x86_64。2026-08至2026-10的旧观察是**历史文档报告的数字**，可以解释当时的优化判断，不能承诺当前容量，也不能视为可独立重复的完整实验包。2026-10-09复测则单独保留源码、环境、原始样本与失败证据。

当前关注查询、商品卡装配、热榜、L1、媒体门禁与封存已变化。旧 M6 每作者 TOP 5/HotRanker 的结果尤其不能套用到现在完整时间线或独立 `/feed/hot`。正确性并发测试证明“不超卖／不重复”，不证明最大吞吐。

## 2026-08-06：小数据框架与连接池基线

单实例本机 macOS，PostgreSQL 16 容器，25 条最大连接；wrk 4.2.0，4 线程、50 并发、10 秒；视频仅 7 条 PUBLISHED。

| 接口 | QPS | 平均延迟 | 当时观测 |
|---|---:|---:|---|
| 未缓存全局 Feed | 12,219 | 4.9ms | db_pool_wait_count 约 12 万，池接近饱和 |
| 登录 | 84.7 | 545ms | bcrypt cost 10，单次哈希约 70ms |

小数据不能代表大规模查询。不要为了提高登录压测数字在没有需求时降低密码哈希成本。

## 2026-08-07：百万视频全局首页缓存 A/B

同机、同容器，100 万 PUBLISHED 视频、3 万用户；vegeta 10 秒、无限速、最多 50 workers；缓存 TTL 60 秒，命中场景先预热。原记录声明两组只改变 FEED_CACHE_ENABLED。

| 场景 | QPS | p50 | p90 | 最大延迟 | 池等待增量 |
|---|---:|---:|---:|---:|---:|
| 无缓存 | 6,576 | 5.4ms | 14.1ms | 220ms | 58,706 |
| 首页缓存命中 | 11,337 | 3.1ms | 6.9ms | 218ms | 0 |

报告缓存命中为 113,378/1（hit/miss，约 99.999%），但 10 秒测试短于 60 秒 TTL，只能说明预热命中路径；不能证明周期失效或混合写入表现。相同数据下吞吐约 1.72 倍、数据库等待减少，是当时保留缓存的依据。

## 2026-08-11：旧关注查询与第一页缓存

3 万用户、100 万视频；关注 0/10/100/1000 的分档用户，各 50 个 token 轮换；vegeta 10 秒、50 workers。旧查询按作者截取 TOP 5，HotRanker 场景是当时实验，均非当前上线行为。

| 关注数 | 无缓存 QPS | 无缓存 p50 / p90 / p99 | 首页缓存 QPS | 缓存 p50 |
|---:|---:|---|---:|---:|
| 0 | 20,414 | 1.7 / 4.2 / 12.5ms | 38,336 | 1.2ms |
| 10 | 4,813 | 9.7 / 14.4 / 23.6ms | 6,995 | 4.6ms |
| 100 | 1,601 | 29.4 / 44.7 / 64.5ms | 6,977 | 4.5ms |
| 1000 | 204 | 240 / 353 / 490ms | 6,578 | 4.7ms |

旧 100 关注 + HotRanker 为 1,171 QPS，p50/p90/p99 为 40.9/57.5/81.1ms。无缓存累计池等待约 115 万；缓存组约 12 万。该实验说明当时重查询可通过首页缓存缓解，但不证明新关注查询性能，也不证明热榜分页正确性。

当前按关注数选查询路径（0 短路，1～32 有界归并，更多走全局索引），见 [repository](../internal/feed/repository.go)。[explain_following.sql](../scripts/explain_following.sql) 的 2026-09-26 旧计划记录：临时表 1000 作者/10 万视频，1000 关注全局索引约 0.07ms、有界归并约 62ms；10 关注约 0.55/0.63ms，10 关注但无作品约 0.23/0.04ms。它只测 SQL，不含完整请求、附加查询和网络，阈值仍需混合负载验证。

## 2026-08-13：同步播放写入与混合读写

单实例 debug 构建、限流关闭；读用 vegeta，播放写用未入库的 Python 临时脚本生成唯一 event_id。不能按旧 `/tmp` 路径声称今天可复现。

| 场景 | QPS | p50 / p90 / p99 |
|---|---|---|
| 空关注首页命中 | 37,946 | 1.2 / 1.8 / 2.4ms |
| 1000 关注首页命中 | 6,249 | 5.2 / 13.7 / 22.3ms |
| 单独播放写，40 workers | 1,640 | 17.2 / 20.9 / 25.2ms |
| 混合读 Feed | 5,840 | 5.5 / 14.8 / 29.1ms |
| 混合写播放 | 528 | 29.3 / 45.4 / 75.7ms |

原记录读吞吐下降约 6.5%，写吞吐下降更明显；它没有支持当时“必须用 Kafka 才能避免写拖慢读”的假设。因此播放异步化暂缓。这个局部结论不意味着所有写负载都不会拖慢读，也不等于已实现 Kafka。

## 2026-10：L1 观察，不是容量测试

原记录只有5次连续请求：第一条冷、后4条 L1 命中，指标 hit=4/miss=2，响应约9ms→2.5ms。这是功能/延迟观察，没有持续压测、双实例或完整负载数据。默认 L1 TTL 5秒、L2 TTL60秒、版本探测1秒的当前值以 [config](../internal/config/config.go) 为准，失效故障窗口见 [ADR-025](architecture-decisions.md)。

缓存穿透历史报告约2,996→5,086 req/s、不存在 ID 的数据库查询降为零，来自旧项目记录；缺少统一原始负载文件，不能当作本轮新实测。Redis 慢命令 Hook 和规则存在是源码事实，不是额外吞吐证明。

## 首轮复测计划（2026-10-09）

目标是给简历提供可复现的缓存优化证据与交易吞吐边界，不预设性能提升。只在现有 PostgreSQL 5432 实例的专用测试数据库、独立 Redis 测试库/键空间中执行，使用同一构建；Feed与交易正式复测已启动，完成结果见下方实测章节。

### P0：先固定测量口径

保存提交SHA与工作区diff、机器架构/CPU/内存、Docker资源上限、Go/PG/Redis版本、数据分布、连接池、日志级别与开关。用同一个编译后的`./bin/api`，固定连接池25，不通过关权限、幂等、账本或持久化来制造对照。容量测试统一关闭限流，限流效果单独验证。

本轮已补齐 [loadgen](../cmd/loadgen/main.go) 的JSON原始样本、实际测量起止时间、创建/支付/完整成功交易分别统计及多个SKU；混合读写仍未实现。准备阶段不计入测量时长，耗尽库存等快速业务失败不计入成功吞吐。另修正DB池等待计数被每次抓取重复累加的问题，历史错误计数不能与本轮直接比较。

压测端自身的CPU、连接、记录延迟的锁/内存也要监控；同机压测注明竞争，无法排除客户端瓶颈时不声称服务达到容量上限。

### P1：Feed 缓存 A/B/C（简历性能项优先）

固定100万PUBLISHED视频、3万用户，首页limit20，相同响应字段和附加查询。造数与假媒体状态只用于读/交易压测，不证明真实媒体校验。三组只改变缓存开关：

| 组 | FEED_CACHE_ENABLED | FEED_L1_ENABLED | 比较目的 |
|---|---|---|---|
| A | false | false | 同一版本直查基线 |
| B | true | false | A→B测Redis L2收益 |
| C | true | true | B→C测L1额外收益 |

先以10/50/100并发各跑30秒摸底；正式先固定50并发，每组预热30秒、持续180秒、重复3轮，并交错组顺序减少漂移。每轮重启API、清理仅属于实验的缓存，再按相同规则预热；保持其他worker和开关相同。180秒覆盖60秒L2 TTL多次失效，不能只保留前10秒高命中结果。

另外记录冷启动首批延迟；对稳定命中、TTL失效回源分别统计。记录成功QPS、P50/P95/P99、业务/系统失败及超时、L1/L2 hit/miss、DB查询/池等待增量、Redis延迟、API与压测端CPU/内存。报告三轮中位数及范围，不挑最高一轮。只在错误率、响应内容与资源条件相当时计算相对收益。

### P2：交易压力与热点边界

固定单SKU请求、每单1件、服务端价格、足够库存；分别测试全部请求落在1个SKU和均匀落在100个SKU，价格/总库存/请求分布明确记录。并发10/50/100，每组120秒、重复3轮；交易测试不用于声称缓存A/B收益。

记录成功创建req/s、成功支付req/s、完整成功订单/s，三种耗时分开；分类库存不足、幂等重放/冲突、超时与5xx。重试/取消/到期竞争单独作为正确性场景，不混入正常吞吐。测试后等待到期事件与投影收敛，核对库存余额、流水、支付事实和九项对账。Outbox区分pending_due/pending_delayed，未来timeout事件不是当前积压。

### P3：混合负载与故障恢复（工程能力项）

先定义负载比：80% Feed读、20%交易流程启动；一笔交易包含创建和支付两次HTTP请求，记录最终实际比例，不能假称请求比例也是80/20。总客户端并发50，持续300秒、重复3轮，对比同条件单独读/单独交易，判断数据库连接池竞争对长尾的影响。

故障实验另测，不能混入正常吞吐：固定中等负载，执行60秒健康→30秒Redis或MinIO不可用→120秒恢复；记录请求结果、熔断前后P95/P99、到期事件积压、投影延迟和恢复时间。先补故障脚本实际动作/断言，避免用现有打印文案当证明；数据库保留事实、重复投递不重复计账、恢复后账实一致分别核验。

### 第二轮，按第一轮发现再选

关注0/10/100/1000与高频作者、深分页、热榜同分/窗口过期、混合发布/删除、双实例缓存失效、缓存穿透，以及慢MinIO大对象封存的锁/池等待。不同排序场景不是相同行为，不拿时间流与热榜差异直接称为优化提升。

原始报告与环境元数据统一保存，汇总仍更新本文，不再建立重复基线文档。结果达到可解释、可重复且账实一致后，才能填入简历的吞吐与P95/P99改善；正确性并发数不换算成QPS。

## 2026-10-09 实测：同版本 Feed 缓存对照

原始证据见 [归档说明](../benchmarks/README.md) 与 `benchmarks/2026-10-09/formal/`。运行在Mac17,3、arm64、10核/32GiB；Docker共享10核/约15.7GiB，容器无单独CPU/内存限制。Go1.26.3、PostgreSQL18.4；API、客户端与容器同机。使用同一API构建、连接池25、默认INFO JSON日志与后台worker；只切换缓存开关，容量测量关闭限流。数据库为新建专用库，Redis为专用DB15。初始100万已发布视频、3万用户，视频为模拟元数据，未读取/播放真实媒体。

匿名全局首页20项，50并发闭环HTTP；每轮重启API、清空专用缓存、预热30秒，再测180秒，各组三轮，顺序ABC/CBA/ABC。这里只证明该请求组合下的对照结果，不声称最大容量。下面是各轮指标的中位数；括号为三轮范围。

| 组 | 成功请求/秒 | P95 ms | P99 ms | 业务/系统失败 |
|---|---:|---:|---:|---:|
| A：直查 | 4,262.8（4,138.4～5,866.6） | 19.11（14.28～19.91） | 26.78（21.25～28.60） | 0 / 0 |
| B：仅Redis | 7,111.6（6,742.5～7,247.5） | 10.21（10.17～10.74） | 20.82（20.26～22.34） | 0 / 0 |
| C：L1+Redis | 8,327.2（8,234.6～8,883.9） | 10.70（9.40～11.13） | 17.21（16.55～17.36） | 0 / 0 |

按三轮中位数，C相对A成功吞吐约+95.3%，P99约−35.7%；B相对A吞吐约+66.8%，C相对B约+17.1%。同轮C/A增幅为51.4%、99.0%、95.3%，存在明显漂移，不能抹去范围。C的P95中位数略高于B，不宣称所有分位数均改善。共10,948,862次成功请求，HTTP200，无业务/系统失败；预热验证首页20项，但未逐请求验证并发写入时内容一致性。

缓存组仍有数据库连接池等待：点赞和商品卡仍按请求装配，不能写“等待归零”。采样用于辅助解释，API/客户端同机、日志与后台任务均竞争资源，不能把本轮数字扩大为线上容量。关注流、深分页、热榜、双实例失效、混合负载与故障恢复尚未测量；不沿用旧版32倍或翻页深度不退化的简历结论。

### 交易复测中止：HTTP吞吐与异步吞吐不匹配

计划18组交易轮次，实际跑完第一轮10并发的1SKU与100SKU两组，在第二组对账失败后停止；未测完50/100并发和第二/三轮。下面只作为问题定位数据，不能给出交易三轮中位数或容量承诺。

| 10并发、120秒 | 完整成功订单/秒 | 订单数 | 完整交易P99 ms | HTTP业务/系统失败 | 测后对账 |
|---|---:|---:|---:|---:|---|
| 单热点SKU | 323.3 | 38,810 | 106.99 | 0 / 0 | 九项无差异 |
| 100分散SKU | 552.8 | 66,351 | 43.51 | 0 / 0 | outbox_delivery有差异，不纳入有效基线 |

每单1件、100分价格、总初始库存100万，商家/买家准备不计入测量；使用模拟支付，无券/退款/视频归因。第二组的订单、支付都是66,351条，库存与流水均933,649、无负库存，但有27,985个PUBLISHED事件缺失消费回执。Redis消费组pending=0、lag=0，Stream只保留10,009条，最早保留消息对应订单56,343。结合`XADD MAXLEN ~ 10000`、单消费者逐条提交，与消费者落后导致未消费消息被裁剪一致；不能只看HTTP200或Redis lag=0判断闭环完成。原始对账只返回前50条差异，27,985来自独立全量计数。

在同一构建上停止新负载，显式调用现有`reconcile --replay --grace 0s`两次；采样缺失回执27,985→6,084→0，最后一次零差异采样在41.19秒，九项对账通过。这个时间是20秒间隔的采样上界，包含重放调用；不是精确恢复时延，更不是默认5分钟周期下的自动恢复SLA。恢复未改账本、未删除回执，也未重建投影。它证明现有补偿可恢复本次缺口，不证明持续负载下自动收敛；本次无视频归因，未验证实际销售投影变更。

下一步先明确Stream保留/裁剪与消费确认的关系，测消费者持续处理能力和峰值积压，验证重放在持续流量下能否收敛；随后重跑完整交易矩阵。不能悄悄把MAXLEN调大、关闭消费者或放宽对账来把本轮失败改成成功。混合读写与主动Redis/MinIO故障实验仍未执行，本次事件重放是发现问题后的单独恢复验证。
