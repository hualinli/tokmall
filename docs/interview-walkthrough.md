# TokMall 面试问题与答案清单（56 题）

这份清单用于理解自己的项目，再练习项目面试。组织形式参考 [GoClub 的 GCFeed 面试清单](https://goclub.space/docs/project-study/gcfeed-interview/)；下面的问题、答法与证据按 TokMall 的代码编写。TokMall 使用 Hertz/PostgreSQL/Redis Streams，没有推荐服务、RabbitMQ、推拉混合 inbox 或消息中心，不借用其他项目的实现与成绩。

> 本轮内容核对：2026-10-13。覆盖简历主线、Feed 专项与最近恢复缺陷修复；性能数字仍引用对应历史实验。

## 第一轮：先把项目讲清楚

### Q01. 项目解决什么问题？怎么用一分钟介绍？

- [ ] 能从用户使用场景介绍项目，再选两个工程亮点展开。

**参考回答：** TokMall 将视频发现与商品交易连接起来：作者发布视频并挂自己的商品，买家从商品卡下单，完成模拟支付、履约或全额退款。后端重点验证并发交易、Feed 缓存分页、异步事件与账实恢复；React 前端用于演示主闭环。

**追问：** 谁是作者、谁是商家？支付是否真实？网页能否用券？同一用户可以承担多个业务身份，资源按 owner ID 授权；支付物流是模拟，券后端已有但网页流程未接。

**证据：** [README 的演示路线](../README.md#第一次演示怎么走)、[业务范围](commerce-business.md)、[前端范围](../web/README.md)。

### Q02. PostgreSQL、Redis、RustFS各负责什么？为什么先做模块化单体？

- [ ] 能画出前端、API、三种依赖和后台任务的关系。

**参考回答：** PG保存订单、库存、状态及Outbox等事实；Redis做缓存、限流、热榜和事件传输；RustFS保存媒体对象。模块分开组织、共享PG，让订单和库存保持本地事务。后台任务与API同进程，当前团队和需求没有要求独立服务部署。

**追问：** Redis停机会不会让PG里的订单消失？拆成微服务会新增什么一致性成本？不能把消息或缓存存储当成交易事实源。

**证据：** [后端架构](backend-architecture.md)、[main装配](../cmd/api/main.go)、[模块化单体](architecture-decisions.md#monolith)。

### Q03. 最后一件库存被两个买家同时买，怎么防超卖？

- [ ] 能写出条件扣减，并说明事务内还包含哪些事实。

**参考回答：** 用 `UPDATE inventory SET quantity=quantity-? WHERE sku_id=? AND quantity>=?` 做原子条件扣减，按影响行数判断成功与不足；余额还有DB CHECK。订单、明细、流水、券和超时事件同事务，失败一起回滚。先准备独立写入，库存更新放在事务尾部，成功后直接提交以缩短持锁时间。

**追问：** “先查库存再减”哪里有竞态？提前写流水后库存不足怎么办？准备记录未提交时不会成为对外可读的业务事实。

**证据：** [订单仓储](../internal/order/repository.go)、[500买家争100件](../internal/order/postgres_integration_test.go)、[不足库存全事实回滚](../internal/order/create_rollback_integration_test.go)、[热点库存锁](architecture-decisions.md#inventory)。

### Q04. 客户端双击或超时重试，如何只生成一单？

- [ ] 能区分同键同载荷重放、同键异载荷冲突和不同键的新请求。

**参考回答：** 幂等范围是 `(user_id,idempotency_key)`，请求指纹包含SKU、数量、来源和券。事务开头按该范围拿 advisory transaction lock，然后查原订单；同载荷返回原单，不同载荷冲突，唯一约束继续兜底。这让券已被首单占用后的同键重试也能先拿到原订单。

**追问：** 为什么只靠订单唯一键不够保证“同键同券”的重放体验？旧实现先锁券，后来的请求会先遇到USED而失败。

**证据：** [Create实现](../internal/order/repository.go)、[同键同券并发测试](../internal/order/coupon_postgres_integration_test.go)、[技术设计](commerce-v1-technical-design.md#创建与幂等)。

### Q05. 支付、取消、发货和退款发生竞争时，状态怎么守住？

- [ ] 能画出订单主状态，并区分履约与退款的允许迁移。

**参考回答：** 支付、取消、超时使用订单行锁、状态条件与流水唯一键。履约命令有独立迁移表，不能复用含退款恢复边的完整状态图。退款仅支持PAID/FULFILLING；拒绝恢复原状态，同意全额退款，未发货回补库存、已发货不回补，COMPLETED不接受退款。

**追问：** 为什么退款申请期间不能发货？曾复用完整状态图而允许错误履约，数据库约束和测试暴露问题；退款恢复边不应成为发货命令的许可。

**证据：** [订单状态机](../internal/order/service.go)、[退款实现](../internal/order/refund_repository.go)、[真实退款竞争测试](../internal/order/refund_postgres_integration_test.go)。

### Q06. 一次Feed请求经过哪些步骤？为什么缓存命中还会访问数据库？

- [ ] 能从路由讲到页面读取、动态装配与响应，不只说“用了Redis”。

**参考回答：** Handler解析参数，Service校验游标并从缓存或仓储拿视频页，按需要复制共享结果，再读取点赞与商品卡、签发相关URL并返回。视频主体可以缓存；点赞、商品关系、商品状态和最低价按请求合并成一次SQL读取，以保留动态新鲜度。

**追问：** 多个商品和SKU一起JOIN会不会把点赞数乘大？点赞和SKU价格先分别聚合再连接。

**证据：** [Feed服务](../internal/feed/service.go)、[合并读模型](../internal/feed/dynamic_read.go)、[计数/新鲜度真实PG测试](../internal/feed/dynamic_read_integration_test.go)。

### Q07. 为什么用游标分页？时间相同的视频怎么办？

- [ ] 能解释排序键、上一页末项、limit+1和游标签名。

**参考回答：** 时间流按 `(published_at,id)` 倒序，有相同时间时用ID形成稳定全序；下一页查询小于上一页末项的记录。多取一条判断has_more。游标带排序版本并由HMAC签名，Base64只是传输编码，不提供防篡改能力。

**追问：** 新视频插到首页是否改变旧游标边界？视频删除或可见性变化是否意味着整个浏览过程是数据库快照？时间游标提供稳定边界，不冻结全站内容。

**证据：** [游标](../internal/feed/cursor.go)、[SQL](../internal/feed/repository.go)、[关注时间线集成测试](../internal/feed/postgres_integration_test.go)、[时间线与热榜](architecture-decisions.md#timeline)。

### Q08. Cache-Aside、singleflight和L1/L2各解决什么问题？

- [ ] 能说明缓存命中、失效、并发回源和共享结果的归属。

**参考回答：** Cache-Aside在miss时回源并回填；singleflight合并进程内同key并发回源，执行前再检查缓存；L1本地LRU减少Redis读取，L2用于共享缓存。回源使用独立超时上下文，避免首个请求取消扩散给其他等待者；装配动态字段前复制共享结果。

**追问：** singleflight能否跨进程合并？发布后远端L1怎样失效？删L2、删本地L1并递增版本，远端定期探测；失败路径依赖TTL兜底，不保证强一致或故障下的固定新鲜度上界。

**证据：** [服务缓存逻辑](../internal/feed/service.go)、[两级缓存](../internal/feed/tiered_cache.go)、[测试](../internal/feed/tiered_cache_test.go)、[缓存一致性](architecture-decisions.md#cache)。

### Q09. 支付提交后进程崩溃，销售统计怎么办？为什么用Outbox？

- [ ] 能指出“提交事实”和“发送外部消息”之间的故障窗口。

**参考回答：** 在同一PG事务写支付事实和Outbox。中继之后发送Streams，发送成功再标记发布，避免事实已提交却没有持久化事件意图。发送成功但标记前崩溃仍可能重发，所以投递是至少一次。

**追问：** 为什么在PG事务里直接发Redis消息也不等于原子提交？PG回滚不能撤销外部发送，两个系统没有共同的本地事务。

**证据：** [Outbox Enqueue](../internal/outbox/model.go)、[中继](../internal/outbox/relay.go)、[真实依赖测试](../internal/outbox/integration_test.go)、[Outbox 与同库事务](architecture-decisions.md#events)。

### Q10. 同一消息收到两次，怎么避免统计重复加？什么时候ACK？

- [ ] 能讲清回执、投影、提交与XACK的先后顺序。

**参考回答：** 消费事务先按 `(consumer,event_id)` 记录唯一回执并执行投影，二者一起提交，再XACK。回执冲突表示该消费者已处理，不重复生效。提交后ACK前崩溃会再次收到消息，但不会再次累计。没有回执表示正常应用路径的消费事务没有生效。

**追问：** 为什么不能人工删回执再重放？若投影仍在，去重依据被删除会造成重复累计。正确恢复依靠缺失回执条件；从事实重建则另需实际消费组回执齐全与维护表锁，详见 Q49。

**证据：** [消费者](../internal/outbox/consumer.go)、[投影](../internal/attribution/projector.go)、[缺失回执测试](../internal/reconcile/missing_receipts_test.go)。

## 第二轮：解释异常与取舍

### Q11. Handler、Service、Repository怎么分工，错误如何传递？

- [ ] 能沿一个订单请求指出三层代码和一个错误映射。

**参考回答：** Handler做HTTP解析、认证身份读取与错误响应；Service做业务规则和用例编排；Repository做SQL/事务并将ORM错误翻译为领域错误。service返回领域视图，model不作为跨层或跨模块API。包装用 `%w`，分类用 `errors.Is/As`，业务拒绝不按系统故障记录。

**追问：** 模块间如何合作而不互相导入业务model？使用消费侧接口和本模块read model，由main装配。账号status零值曾绕过DB默认值导致注册后无法登录，说明ORM写入与数据库默认值也要验证。

**证据：** [订单Handler](../internal/order/handler.go)、[Service](../internal/order/service.go)、[仓储](../internal/order/repository.go)、[注册后登录真实PG测试](../internal/user/postgres_integration_test.go)。

### Q12. 订单过期后收到支付请求，为什么不能在事务内直接返回过期错误？

- [ ] 能区分“业务请求失败”与“必须提交的关单副作用”。

**参考回答：** 支付路径做lazy expiry，写EXPIRED、回补库存与释放券。这些副作用要提交；事务闭包直接返回错误会一起回滚。实现先提交过期处理，再在事务外返回订单已过期。延迟事件加速关闭，轮询worker提供安全网。

**追问：** 三条超时路径同时到达会不会重复回补？订单行锁、状态条件和账本唯一键共同守住一次生效。

**证据：** [支付/过期仓储](../internal/order/repository.go)、[超时处理](../internal/order/timeout_handler.go)、[竞争测试](../internal/order/postgres_integration_test.go)、[支付、取消与超时](commerce-v1-technical-design.md#支付取消与超时)。

### Q13. 券怎么防超发、重复使用和关单后无法重用？

- [ ] 能说明发券/领券/下单核销的锁与唯一约束，以及金额规则。

**参考回答：** 领取锁模板、条件更新发行量并检查用户限领；下单锁持券，检查归属、同商家、有效期和门槛，以集中规则计算折扣。订单满足 `original-discount=total` 且实付大于零。取消、超时和退款成功退券；历史订单保留引用，部分唯一索引只限制仍占券订单。

**追问：** 过期券退回什么状态？能否叠券或跨商家？退为EXPIRED；当前只有同商家满减，一单一券。

**证据：** [券规则](../internal/coupon/service.go)、[领取竞争测试](../internal/coupon/postgres_integration_test.go)、[用券/关单测试](../internal/order/coupon_postgres_integration_test.go)、[迁移000024](../migrations/000024_closed_order_coupon.up.sql)。

### Q14. 热榜如何保持翻页稳定？Redis坏了怎么处理？

- [ ] 能区分热榜快照与时间流，也能说明首页和后续页的降级差异。

**参考回答：** 点赞/播放写分钟桶，后台物化冻结v2窗口，最多2000项、TTL10分钟。游标包含窗口、分数和ID；窗口不重写，到期拒绝旧游标。空首页或首页Redis故障可降级时间流；返回时间游标后继续时间流。已有热榜游标遇故障返回错误，避免途中换排序。

**追问：** 包里的HotRanker能直接用于关注分页吗？它是实验路径，生产Service只接受TimeRanker。播放event_id幂等也不等于有效播放防刷。

**证据：** [热榜](../internal/feed/hot_cache.go)、[服务/分页测试](../internal/feed/hot_service_test.go)、[Ranker测试](../internal/feed/ranker_test.go)、[冻结热榜](architecture-decisions.md#timeline)。

### Q15. 关注Feed是推还是拉？为什么不只取每个作者最近五条？

- [ ] 能说明当前查询策略和未来推拉混合的进入条件。

**参考回答：** 当前拉模式读完整关注时间线；无关注短路，小集合按作者有界召回再归并，大集合走全局时间索引过滤。每作者固定TOP5会永久丢掉更旧作品，不符合完整时间线。用户第一页缓存按关注关系失效，发布/删除不遍历全部粉丝key，靠TTL收敛。

**追问：** 大V和大量关注时怎样扩展？先测读取成本，再评估推送inbox或混合模式；当前没有交付fanout。

**证据：** [关注SQL](../internal/feed/repository.go)、[完整时间线测试](../internal/feed/postgres_integration_test.go)、[查询计划脚本](../scripts/explain_following.sql)。

### Q16. 点赞、关注、播放的幂等有什么差别？

- [ ] 能说明关系存在性与事件载荷一致性的不同约束。

**参考回答：** 点赞/关注由唯一关系配合ON CONFLICT避免重复关系。播放同步落PG，event_id必须绑定一致载荷；重放不重复计数，同ID换视频或其他事实返回冲突。每个新event_id仍可产生新播放，因此未实现同用户同视频时间窗口的有效播放去重。

**追问：** 幂等能否防一个用户刷热榜？不能把重试去重当反作弊；有效播放口径尚待定义。

**证据：** [互动仓储](../internal/interaction/repository.go)、[播放仓储与Service](../internal/video/repository.go)、[后续计划](roadmap.md)。

### Q17. 如何处理大量不存在的视频ID？Bloom会不会误伤合法请求？

- [ ] 能区分真实不存在、未发布不可见和过滤器尚未加载。

**参考回答：** 本地Bloom阴性不能证明数据库不存在：其它实例的新数据可能尚未同步。因此阴性也继续查共享负缓存和DB，首次加载前放行。重建成功才切换，本地新增双写构建缓冲，失败保留旧集合。负缓存只存DB真实miss，不能记录未发布但不可见的视频。

**追问：** 新发布内容还没进入过滤器怎么办？单实例增量更新解决不了跨实例同步，不能把Bloom的数学性质扩大成数据库完整性保证；当前选择放行，接受首次miss的查询成本。

**证据：** [存在性防护](../internal/existence/)、[视频读路径](../internal/video/existence.go)、[缓存边界](architecture-decisions.md#cache)。

### Q18. 为什么媒体先上传staging，再复制到最终对象？

- [ ] 能说明签名、票证、对象大小检查和ETag条件封存。

**参考回答：** 客户端只获得临时key的预签名PUT，签名绑定声明长度/类型；封存时校验实际大小并按源ETag复制最终key，避免检查后被替换。票证归属、到期和核销受PG事务与行锁保护，视频创建与票证核销同事务。

**追问：** RustFS复制成功但PG提交失败会怎样？外部副作用不能回滚，可能留下未知final孤儿；当前没有扫描回收这类对象的完整机制。

**证据：** [上传服务](../internal/video/service.go)、[存储契约测试](../internal/storage/upload_integration_test.go)、[封存与清理](architecture-decisions.md#media)。

### Q19. 文件已经上传，为什么还要异步校验后才发布？

- [ ] 能区分PENDING、PASSED、REJECTED与SKIPPED。

### Q27. 怎样设计一次可信的压测？并发、RPS、订单TPS有什么区别？

## 第四轮：Feed 专项深入追问

### Q33. 为什么只缓存默认大小的首页，不把所有分页都缓存？

- [ ] 能比较命中率、key 数量、内容新鲜度和失效成本。

**参考回答：** 当前全局流和关注流只有默认 limit、无游标的首页走页缓存。首页复用度高，深页游标分散，缓存所有组合会增加 key 数量和失效成本。自定义 limit 也回源，避免把固定大小首页返回给不同大小的请求。热榜已有 Redis 物化窗口，不额外建立每个游标的页面缓存。

**追问与答法：** 如果深页访问很多怎么办？先测游标复用率和 SQL 成本，再考虑有容量上限的深页缓存；不能只因为“缓存快”就缓存所有查询。

**证据：** [List/ListFollowing](../internal/feed/service.go)、[缓存 key](../internal/feed/cache.go)、[热榜读取](../internal/feed/hot_service.go)。

### Q34. 为什么没有照搬“ID 页、详情、计数”三份缓存？

- [ ] 能说明当前缓存保存什么，以及不同缓存粒度的代价。

**参考回答：** 当前首页缓存视频主体响应，点赞和商品卡在请求时批量装配，不是完全的 ID-Detail 分离。这样减少了缓存层数，保留商品状态和价格的新鲜度，但命中首页缓存仍会访问 PG。若实测动态读取成为瓶颈，可分别评估稳定详情缓存、计数短缓存或聚合读模型，每种方案都需要自己的失效与恢复规则。

**追问与答法：** 计数缓存后商品价格也可以一起缓存吗？计数展示与价格展示的新鲜度要求不同，不能共用一个拍脑袋的 TTL；无论前端显示什么，下单仍需从服务端事实重新确认价格和可售状态。

**证据：** [FirstPageCache](../internal/feed/cache.go)、[动态读模型](../internal/feed/dynamic_read.go)、[下单快照](../internal/order/repository.go)。

### Q35. 删缓存加版本号，能保证永远不读旧数据吗？

- [ ] 能画出回源、业务写入、失效、旧结果回填之间的交错。

**参考回答：** 不能。缓存失效可能失败，远端版本读取也可能失败；此外，在途请求可能先读到旧数据库结果，等另一个请求提交并失效后，再把旧结果写回。版本通知不是对所有回填的原子保护。当前应按最终一致解释，不能承诺删除后所有首页立即消失，也不能把版本探测间隔当成全部故障下的陈旧上界。

**追问与答法：** 如果要求更严格怎么办？可评估回源前后版本校验、带版本的 key 或条件回填，以及读时可见性校验；需要确定性并发测试与双实例实验。它们是增强方向，不是当前都已交付。

**证据：** [两级缓存](../internal/feed/tiered_cache.go)、[回源回填](../internal/feed/service.go)、[缓存边界](roadmap.md)。

### Q36. 热榜快照里的视频被删除了，游标该怎么推进？

- [ ] 能区分“排名快照稳定”与“内容可见性不变”。

**参考回答：** 热榜先取排名条目，再批量查当前仍已发布的视频，删除或不可见项会被跳过。游标按本轮扫描的最后一个排名条目推进，不按过滤后最后一个可见项推进，避免反复扫描失效项。当前没有循环补满页面，因此过滤后可能少于 limit，甚至空页但仍有后续条目；冻结的是排名，不是所有业务字段。

**追问与答法：** 要保证页面尽量满怎么办？有界地继续扫描并补齐，同时限制最大扫描量，游标始终记录实际扫描边界；不能为了补满无限读取，也不能因一页为空就重启榜单。

**证据：** [ListHot/loadHotItems](../internal/feed/hot_service.go)、[ListByIDs](../internal/feed/repository.go)、[热榜连续翻页测试](../internal/feed/hot_service_test.go)。

### Q37. 关注流为什么以 32 个作者为查询策略分界？

- [ ] 能解释两条查询路径为何返回相同语义，以及阈值的证据等级。

**参考回答：** 少量关注时，对每个作者利用索引取游标后的 limit+1 条，再统一归并；关注很多时，大量逐作者查询成本上升，因此改用全局时间索引结合关注关系过滤。32 是合成数据执行计划对比得到的工程阈值，不是通用常数。两条路径都返回完整时间线的下一页，不能通过每作者固定五条来换性能。

**追问与答法：** 关注 1000 个几乎不发视频的作者会怎样？全局扫描可能为了凑齐一页过滤大量无关视频。需要把关注数、作者活跃度、时间分布与页深一起测，不能只测粉丝数或首页。

**证据：** [followingMergeMaxAuthors](../internal/feed/repository.go)、[完整时间线测试](../internal/feed/postgres_integration_test.go)、[EXPLAIN 脚本](../scripts/explain_following.sql)。

### Q38. 页面写“为你推荐”，是否实现了个性化推荐？

- [ ] 能主动区分界面命名、在线排序与实验代码。

**参考回答：** 没有。该标签目前接全局时间流，在线关注流也只允许 TimeRanker；独立热榜提供群体热度排序。包中的 HotRanker 是单元实验，不能把排序函数存在等同于推荐系统完成。我还没有交付用户画像、曝光过滤、作者打散或个性化召回。

**追问与答法：** 最小推荐版本怎么做？先定义行为反馈，再做最新/热门/关注内容多路召回、简单标签偏好排序、近期曝光过滤与作者打散。用短期会话快照稳定翻页。没有真实用户实验时只报告延迟、填充率和重复率，不宣称提高留存。

**证据：** [页面入口](../web/src/routes/index.tsx)、[Ranker 能力约束](../internal/feed/ranker.go)、[服务门禁](../internal/feed/service.go)。

### Q39. 播放事件幂等了，为什么仍不能拿它当有效播放？

- [ ] 能区分进入展示、成功起播、有效观看、完播和反作弊。

**参考回答：** 当前前端在组件启用上报时生成 event_id；Feed 激活卡片就触发，可能早于播放成功，未登录用户不报，上报失败也不阻塞播放。后端保证同事件载荷一致与重试去重，但新 event_id 仍可新增计数。因此这是当前播放事件口径，不是严格的有效观看或防刷证明。

**追问与答法：** 怎样改进？分别定义曝光、实际起播、累计观看时长、完播；处理循环播放、自动播放失败和重复上报。服务端限制不合理时长与请求频率，明确客户端信号仍可伪造。当前这些属于下一步工作。

**证据：** [播放上报](../web/src/features/video/use-play-report.ts)、[卡片激活](../web/src/features/feed/feed-card.tsx)、[播放幂等规则](../internal/video/service.go)。

### Q40. 如果改成推拉结合关注流，最难的部分是什么？

- [ ] 能描述未来设计的失败路径，不把它说成现有能力。

**参考回答：** 当前仍是拉模式。未来可让小作者发布后分批写粉丝 inbox，大作者保留作者内容索引供读时合并。难点是发布事件可靠落地、分批断点、重复投递、新关注回填、取消关注过滤，以及作者策略切换时不漏项。还要限制索引长度并为历史翻页回源，保留当前完整时间线语义。

**追问与答法：** 作者 outbox 和 Transactional Outbox 是一回事吗？不是。前者是作者内容索引，后者记录与业务事实同事务提交的事件意图。也不能把 Redis fanout 与 PG 回执说成一个本地事务。

**证据：** [当前拉模式](../internal/feed/repository.go)、[事件事务边界](../internal/outbox/model.go)、[未来工作](roadmap.md)。

## 第五轮：交易与数据约束追问

### Q41. 客户端改商品价格、商家 ID 或来源作者能否便宜下单？

- [ ] 能说明哪些字段来自服务端，以及来源校验能证明什么。

**参考回答：** 下单由服务端读取可售 SKU、商品及商家，计算金额并保存订单项快照，不直接相信客户端价格。若传来源，校验商品一致及有效推广关系，再记录来源快照。不过当前来源由客户端提供，只证明关系存在，不证明真实点击；归因统计不能直接拿去做佣金结算。

**追问与答法：** 下单后改价会改变旧订单吗？不会，旧订单使用当时快照。并发下架或改价的生效边界则需结合事务读时点解释，不能声称当前已对所有商品修改建立全局串行化。

**证据：** [findSellableSKU/Create/requireActiveSource](../internal/order/repository.go)、[订单项模型](../internal/order/model.go)。

### Q42. 金额为什么不用浮点数？用整数就完全安全吗？

- [ ] 能说明单位、溢出检查和金额约束。

**参考回答：** 金额用整数最小货币单位表示，避免二进制浮点在十进制金额计算中的舍入问题。计算单价乘数量前检查正值和 int64 溢出，折扣由集中规则计算，数据库约束原价减优惠等于实付，当前不接受实付为零。整数解决表示问题，不自动解决业务计算和边界问题。

**追问与答法：** 以后增加比例折扣、税费或多币种怎么办？需单独定义舍入规则、币种和最小单位，并让订单快照固定这些事实；不能把当前满减模型直接推广到所有金额场景。

**证据：** [multiplyAmount](../internal/order/repository.go)、[DiscountFor](../internal/coupon/service.go)、[金额边界测试](../internal/order/repository_test.go)。

### Q43. 同一个支付单号被用于不同订单，如何处理？

- [ ] 能区分“重复成功返回”与“支付身份被换载荷复用”。

**参考回答：** 支付事务锁定归属当前用户的订单，按支付身份查已有记录。重放必须匹配原订单、金额及支付身份，否则返回幂等冲突；相关唯一约束兜底并发插入。支付记录、订单变为 PAID 和支付事件同事务提交，不允许把另一单的成功支付记录拿来完成当前订单。

**追问与答法：** 网络超时是否表示支付失败？不一定，数据库可能已经提交。客户端应用相同业务身份查询或重试，不能每次随机换支付身份。目前接口是模拟支付，不具有真实渠道扣款语义。

**证据：** [Pay/findPaymentByIdentity/sameSuccessfulPayment](../internal/order/repository.go)、[支付并发测试](../internal/order/postgres_integration_test.go)。

### Q44. 有库存余额了，为什么还需要流水和对账？

- [ ] 能说明余额、操作证据与差异检测各自的职责。

**参考回答：** 余额支持高效读取和条件扣减；流水保存调整、下单扣减、关单回补或退款回补的原因与业务标识。流水唯一键防止同一业务动作重复登记，流水与余额同事务变化。对账再检查余额与流水总和、订单状态与对应流水是否匹配，发现绕过正常路径的手工改库或历史错误。

**追问与答法：** 发现余额与流水不符，直接把余额改成流水和吗？不能先假定哪一侧可信。先定位差异来源、确定业务事实，再按批准的恢复方案处理；现有对账不会自动改库存事实。

**证据：** [库存模块](../internal/inventory/repository.go)、[订单回补](../internal/order/refund_repository.go)、[对账 SQL](../internal/reconcile/repository.go)。

### Q45. 券退回后，为什么历史订单的券引用不清空？

- [ ] 能区分历史事实与当前资源占用。

**参考回答：** 订单仍需解释当时的原价、优惠和实际支付，因此保留历史券引用。取消、到期或退款成功后，持券恢复 UNUSED 或过期为 EXPIRED；唯一索引只约束仍占券的订单，允许有效券再次使用。若所有历史订单都参与唯一约束，退回的券也会被旧订单永久挡住。

**追问与答法：** 可以只删唯一索引吗？不应无条件删掉占用约束。需要同时保留持券行锁、条件核销与只约束当前占用的唯一索引，并验证重试、取消和再使用的组合。

**证据：** [迁移 000024](../migrations/000024_closed_order_coupon.up.sql)、[退券规则](../internal/order/refund_repository.go)、[券订单竞争测试](../internal/order/coupon_postgres_integration_test.go)。

### Q46. 接真实支付时，现有模拟支付要改哪些地方？

- [ ] 能说明新增协议与补偿边界，不声称已经完成渠道接入。

**参考回答：** 需要区分客户端支付意图与渠道回调，新增验签、商户和金额核验、渠道交易身份与幂等；明确关单和晚到成功回调如何协调，并建立主动查单、退款重试及渠道对账。外部扣款无法与 PG 一起回滚，不能把现有模拟支付事务直接包住渠道请求就称为原子支付。

**追问与答法：** 渠道扣款成功但本地超时怎么办？保持可查询的中间状态，按渠道幂等身份查单并补偿；根据确认结果完成本地状态或退款，而不是仅凭网络错误把钱当作没扣。这是未来设计，当前未实现。

**证据：** [当前模拟支付](../internal/order/service.go)、[业务边界](commerce-business.md)、[真实资金计划](roadmap.md)。

## 第六轮：故障恢复与最近修复

### Q47. 为什么双缓冲 Bloom 仍曾把已有视频判成不存在？

- [ ] 能讲清错误指针、第二次重建和失败后的影响。

**参考回答：** 原逻辑创建 standby，却把全量数据写入 active；交换后完整数据在旧缓冲，第二次重建会清掉它。一轮交换后的查询还能命中旧缓冲，所以原测试没发现问题。修复为独立 building，成功才切换 active，失败保留旧集合；本地新增在构建期间双写，并串行化同一集合的重建。

**追问与答法：** 为什么修好轮换后还取消了阴性直接 404？轮换正确不等于跨实例数据同步完整。A 新建而 B 未同步仍是反例，所以本地阴性继续走负缓存/DB。代价是随机不存在 ID 的首次请求仍需回源。

**证据：** [Rebuild/Add](../internal/existence/guard.go)、[多轮重建、并发新增及多实例测试](../internal/existence/guard_test.go)、[正确性与恢复边界](architecture-decisions.md#recovery)。

### Q48. 负缓存能不能缓存所有 404？它有什么边界？

- [ ] 能区分资源不存在与资源不可见。

**参考回答：** 不能。对非作者不可见的未发布视频也返回 404，但数据库记录存在，写入共享负缓存会影响有权读取的作者。只记录真实 DB miss，并用 TTL 抖动限制保留时间。负缓存表示某个查询时刻不存在，不是永远不存在；预测未来 ID、创建与 miss 并发等情况还需评估失效窗口。

**追问与答法：** Redis 不可用是不是返回 404 更省事？不是，应放行到数据库。缓存失败只能降低防护效果，不能被伪装成资源不存在；同时要用入口保护避免数据库被回源洪峰压垮。

**证据：** [MayExist/MarkMissing](../internal/existence/guard.go)、[视频可见性路径](../internal/video/service.go)、[负缓存测试](../internal/existence/guard_test.go)。

### Q49. 为什么“投影可以从事实重建”还会导致 GMV 翻倍？

- [ ] 能复述 200 → 400 的触发顺序和现在的拒绝条件。

**参考回答：** 支付事实已提交但事件未消费，重建先把 200 计入日销；旧事件随后到达，因为没有回执，又加 200。正常消费的回执与投影同事务，并不保护绕过回执的重建路径。现在必须指定实际消费组，支付/退款事件回执齐全，并对事实、回执和投影相关表取得 NOWAIT 维护锁，才允许重建。

**追问与答法：** 只暂停消费者够吗？不够，恢复后旧事件仍会到达。应先暂停相关业务写入、处理并排空事件，再暂停相关后台写入并重建。未来 timeout 不参与支付/退款回执门禁；未消费退款会阻止重建。大表在线重建需要另外设计快照与增量衔接。

**证据：** [重建门禁](../internal/reconcile/repository.go)、[延迟事件、重复投递和维护争锁测试](../internal/reconcile/rebuild_integration_test.go)、[运维流程](development-and-operations.md#观测与恢复)、[正确性与恢复边界](architecture-decisions.md#recovery)。

### Q50. 为什么消费者一直运行，PEL 尾部消息仍可能没恢复？

- [ ] 能说明扫描位置与超时资格是两个不同条件。

**参考回答：** 原先每次 XAUTOCLAIM 都从起点扫描并丢弃后续位置。前方存在大量尚未达到 idle 阈值的 pending 时，有界扫描可能一直触达不了后面的超时消息。现在用分页 XPENDING 获取同页消息与次数，再由 XCLAIM 原子检查 MinIdle；即使本页没有可认领项，也推进位置，到末尾绕回。

**追问与答法：** 次数查询失败能当零继续吗？不能，否则毒丸可能逃过 DLQ 阈值。现在查询失败不认领、不推进游标；进程重启从头扫描仍安全，但恢复时间随 PEL 页数和扫描周期增长，没有固定秒级 SLA。

**证据：** [ClaimOnce](../internal/outbox/consumer.go)、[尾部与绕回测试](../internal/outbox/claim_pagination_test.go)、[次数查询故障测试](../internal/outbox/deadletter_test.go)。

### Q51. Redis 持久化丢了一段消息，Transactional Outbox 就一定能自动恢复吗？

- [ ] 能区分未发布重试、已发布缺失回执重放和死信处理。

**参考回答：** 未发布事件仍由中继重试；已标记 PUBLISHED 但目标组缺回执的事件，可在宽限期后由对账重新入队，沿用 event_id 去重。这个恢复依赖 PG 中事件与事实仍完整、消费回执可信、消费者及对账运行正常。DEAD 与消费 DLQ 另有处理路径，不能把所有失败都说成自动恢复。

**追问与答法：** 消费速度一直低于生产速度，重放能解决吗？不能。重放恢复缺失，不创造处理能力；背压把待投递事件留在 PG，长期仍需降低入口负载或提高消费能力，并监控最老待处理年龄与磁盘增长。

**证据：** [中继](../internal/outbox/relay.go)、[缺失回执重放](../internal/reconcile/service.go)、[安全保留](../internal/outbox/transport.go)。

### Q52. 为什么把数据库连接池分成 20+5，而不是直接扩大到 50？

- [ ] 能区分资源预算隔离与数据库容量扩张。

**参考回答：** 热点订单在库存锁上等待时仍占用连接，共享池被前台耗尽后消费者拿不到连接，事件积压更严重。当前保持总上限 25，前台及普通后台 20、消费者保留 5，防止前台占完消费预算。它不隔离 PG CPU、磁盘或行锁，5 条连接也不等于当前有 5 路并行消费者。

**追问与答法：** 扩连接一定提高吞吐吗？不一定，可能只是把排队搬进 PG。实验中预算隔离改善消费获取资源，但不能宣称 HTTP 吞吐因此上升；需要把吞吐、长尾和消费收敛一起报告。

**证据：** [装配](../cmd/api/main.go)、[连接池隔离测试](../internal/database/pool_integration_test.go)、[预算实验](../benchmarks/2026-10-12/step2-consumer-budget/README.md)、[库存与连接预算](architecture-decisions.md#inventory)。

## 第七轮：直接对应简历的综合问答

### Q53. 讲一次你定位并修复的复杂问题。

- [ ] 能按现象、假设、证据、修复、限制讲两分钟。

**参考回答：** 可以选事件裁剪问题：HTTP 下单支付成功，但测后对账发现事件缺少回执；当时 Redis pending/lag 却为零。我沿 PG event_id 追踪成功 XADD 的 Stream ID，发现缺失消息早于保留边界，且不在 Stream/DLQ。扩大保留上限的诊断对照能完成消费，定位到长度裁剪删除未消费消息。正式方案改为按所有消费组确认水位回收，满容量时背压回 PG，并补多组与乱序 ACK 测试。

**追问与答法：** 修完还有什么问题？消费能力不足仍会积压，背压保证保留意图而不是保证无限吞吐。不能只用“大缓冲下跑通”作为最终修复。

**证据：** [诊断原始记录](../benchmarks/2026-10-11/diagnosis/README.md)、[保留策略测试](../internal/outbox/retention_integration_test.go)。

### Q54. 你怎么证明测试不是只把实现抄一遍？

- [ ] 能给出一个旧实现必失败、修复后通过的可观察反例。

**参考回答：** 我会验证业务不变量和失败交错。例如过滤器必须在第二轮重建失败后仍保留已有 ID；实例 A 新增后，B 不得仅因本地 Bloom 阴性拒绝查询；存在未消费支付事件时，重建必须拒绝且不改投影；PEL 的尾部超时消息必须最终被扫描到。这些测试针对用户可见行为或账务结果，不只断言某个私有函数被调用。

**追问与答法：** mock 能证明行锁安全吗？不能，锁竞争、唯一约束和回滚需要真实 PG；认领、重试次数和裁剪需要真实 Redis。竞态检测只能发现被执行路径上的 Go 数据竞争，也不能代替跨系统一致性测试。

**证据：** [过滤器测试](../internal/existence/guard_test.go)、[重建测试](../internal/reconcile/rebuild_integration_test.go)、[PEL 测试](../internal/outbox/claim_pagination_test.go)、[交易竞争测试](../internal/order/postgres_integration_test.go)。

### Q55. 简历上的“提升 43%、完成 25.2 万单”具体是什么？

- [ ] 能解释两个数字来自不同实验，不能拼成一个生产容量结论。

**参考回答：** 43% 来自 10 月 12 日同机热缓存 Feed 首页对照：相同前台 20/消费 5 连接预算、100 并发、两组各 60 秒三轮，合并动态查询后吞吐中位数从 6484.0 到 9269.6 请求/秒；P99 中位数从 43.15 到 39.89 毫秒，两组均零请求错误与页面检查失败。它适用于当时稀疏点赞/商品数据，不代表所有场景。

25.2 万单来自库存临界区调整后的六轮交易测试，共 252256 单，涵盖热点与 100 SKU 分散场景。测后等待消费收敛，再核对库存、账本、支付、回执、投影和九项对账。它证明这些有限时长实验的闭环正确性，不等于线上订单量，也不是持续负载最大容量。

**追问与答法：** 为什么不继续写原来的 32 倍和连接池等待归零？早期实现、场景和数据口径不同，不能作为当前版本结论。最近的库存优化前只有单轮参考，也不能包装成严格三轮 A/B；后续修复未重新压测，不将历史成绩改称最终代码的新测结果。

**证据：** [Feed 三轮对照](../benchmarks/2026-10-12/step3-feed-dynamic/README.md)、[交易六轮结果](../benchmarks/2026-10-12/step4-stock-lock/README.md)、[证据适用范围](performance-baseline.md)。

### Q56. 如果再给你两周，你会补什么？为什么不先上微服务？

- [ ] 能按风险和证据选工作，而不是罗列技术栈。

**参考回答：** 我优先补双实例下的 Feed 发布/删除/翻页与依赖故障实验，把现有故障演练改成真正触发故障并有恢复断言，再测固定到达率读写混合负载。如果目标转向 Feed 专项，再定义曝光和有效播放，构建小规模推荐闭环。当前拆服务不会自动解决库存热点、回源洪峰或消费不足，反而增加跨服务事务和运维成本。

**追问与答法：** 什么情况下才会改变优先级？如果测量表明某模块需要独立扩缩容、故障隔离或团队独立交付，再评估拆分；关注拉模式的真实负载超出预算，才推进推拉结合。每次演进都先写触发条件和验收指标。

### 容易失分的表述

| 不要直接说 | 更准确的答法 |
|---|---|
| Bloom 没有假阴性，所以能直接挡不存在 ID | 数学性质只针对已插入集合，本地同步不完整时不能证明数据库不存在 |
| 加事务就能保证支付和发消息一起成功 | 事实与 Outbox 同 PG 事务，外部投递至少一次，消费幂等 |
| 删缓存就强一致，远端最多旧一秒 | 存在失效失败、版本读取失败和在途回填竞争，当前按最终一致解释 |
| 日销是派生数据，随时重建即可 | 必须满足实际组回执齐全和维护锁条件，未消费事件可能重复累加 |
| pending=0 所以业务处理完了 | 还需检查未读 lag、PG 待投递事实、目标组回执和业务投影 |
| 有播放 event_id 就能防刷 | 事件重试幂等不等于有效观看去重或反作弊 |
| Redis 挂了回源就算容灾完成 | 还需要验证数据库预算、入口保护和故障负载，不承诺无损降级 |
| 25.2 万单证明生产可用 | 这是限定条件的本机实验，未涵盖长期容量、真实支付和所有故障 |

遇到尚未实现的问题，先说清现状，再解释方案和验证方法。没有做过的实验不要编成经历；能指出限制并给出可检验的下一步，比背完整套术语更可信。
