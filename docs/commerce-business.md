# 商城业务梳理（Product / Business View）

> 本文档从产品经理视角梳理 TokMall 的商城业务，作为后端设计、前端页面和数据模型的统一输入。
> 技术落地细节见 `docs/content-commerce-backend-agent-guide.md` 和后续 ADR。

## 1. 业务定位

TokMall 不是“另一个电商平台”，而是**短视频内容电商**：

- 用户因为内容（视频）产生购买动机
- 作者是内容创作者 / 带货推广者，不一定是商家
- 商家 / 平台拥有商品、库存和订单
- 系统需要回答：“这个作者带来了多少交易？”

一句话：**内容是流量入口，交易是转化终点，作者是归因渠道。**

## 2. 核心角色

| 角色 | 说明 | 关键诉求 |
|---|---|---|
| 普通用户 | 浏览 Feed、看视频、点赞关注、点击商品、下单 | 看到感兴趣的商品，购买流程顺畅，能查订单 |
| 作者 / 创作者 | 发布视频，在视频中挂商品链接，帮商家带货 | 能选择可推广商品，查看自己带来的订单/人数/佣金 |
| 商家 / 平台 | 创建商品、管理库存、处理订单、创建秒杀活动 | 商品可售、不超卖、订单状态准确、能结算 |
| 平台运营 | 审核内容、管理活动、查看转化漏斗 | 内容合规、活动可控、数据可分析 |

> 重要区分：**作者不等于商家。**
> 作者是“推广渠道”，商家是“商品所有者”。一个作者可以带多个商家的货；
> 一个商品也可以被多个作者推广。

## 3. 核心业务目标

1. 让用户能在视频场景里完成“看到 -> 感兴趣 -> 购买”的闭环。
2. 让作者能通过带货获得收益，并能看到自己的带货效果。
3. 让商家/平台能安全地管理库存和订单，不超卖、不重复下单。
4. 让系统能准确归因每一笔订单来自哪个作者/视频，用于结算和运营分析。

## 4. 核心用户故事

### 4.1 普通用户

- 我在 Feed 里刷到一条视频，视频下方有商品卡。
- 我点击商品卡，能进入商品详情页。
- 我下单时，系统能记住我是从哪个作者的哪个视频点进来的。
- 我可以在订单列表看到自己的订单状态。
- 我可以对未支付订单取消，对已支付订单申请售后（后续版本）。

### 4.2 作者 / 创作者

- 我发布视频时，可以从可推广商品列表中选择商品挂到视频上。
- 我可以在“带货中心”看到每个商品的曝光、点击、订单人数、订单数、GMV。
- 我不需要管理库存和发货，只关心推广效果和佣金。
- 我下架某个商品后，之前发布的视频仍然存在，但商品卡变为不可购买。

### 4.3 商家 / 平台

- 我创建商品和 SKU，设置价格、库存和上下架状态。
- 我可以查看所有订单，处理发货。
- 我可以创建秒杀活动，设置活动库存和活动时间。
- 我需要防止超卖、重复下单和恶意刷单。

### 4.4 平台运营

- 我可以看到“视频 -> 商品点击 -> 下单 -> 支付”的转化漏斗。
- 我可以按作者、按视频、按商品维度分析带货效果。
- 我可以审核商品和内容。

## 5. 核心业务流程

### 5.1 视频带货闭环

```text
商家创建商品 / SKU / 库存
        ↓
作者发布视频，选择要挂的商品
        ↓
Feed / 视频详情展示商品卡
        ↓
用户点击商品卡
        ↓
进入商品详情页
        ↓
下单 -> 支付 -> 订单完成
        ↓
系统记录订单归因（作者、视频、商品）
        ↓
作者带货中心展示数据
```

### 5.2 普通下单流程

```text
用户提交订单
  -> 服务端校验商品状态
  -> 服务端重新读取价格，不信任客户端价格
  -> 原子扣减库存
  -> 创建订单（状态：CREATED / PENDING_PAYMENT）
  -> 用户支付（模拟支付）
  -> 订单变为 PAID
  -> 商家发货 -> FULFILLING -> COMPLETED
```

### 5.3 秒杀流程（后续版本）

```text
活动开始前：展示活动商品和倒计时
活动开始：用户点击秒杀
  -> 限流
  -> 资格校验
  -> Redis 预扣 / 数据库条件扣减
  -> 创建订单
  -> 异步削峰（Kafka / Worker，按需引入）
  -> 超时未支付回补库存
```

## 6. 功能范围

### Commerce v1（本轮要做）

- 商品：商品列表、商品详情、上下架
- SKU：规格、价格、库存
- 普通下单：创建订单、订单详情、订单列表
- 模拟支付：受 JWT 保护的买家模拟支付命令、重复请求幂等（真实渠道回调另设适配器）
- 订单状态机：创建 -> 待支付 -> 已支付 -> 发货中 -> 完成；可取消/超时关闭
- 视频挂商品：视频与商品关联，Feed/视频详情返回商品卡
- 订单归因：记录 `author_id` / `video_id` / `product_id`
- 作者带货数据：按作者统计订单数、购买人数、GMV

### Commerce v2（后续再做）

- 秒杀活动
- 购物车
- 优惠券
- 售后 / 退款
- 佣金结算
- 多商家 / 店铺
- 复杂营销归因（多触点归因）

### 明确不做

- 真实支付渠道
- 复杂税率 / 多币种
- 真实物流
- 开放平台 / 商家后台完整权限体系
- 一开始就上 Kafka / 微服务

## 7. 关键业务规则

### 7.1 商品

- 商品属于商家/平台，不属于作者。
- 商品下架后，已挂载的视频仍可展示，但商品卡应显示“已下架/不可购买”。
- 下单时必须重新读取商品最新价格和状态，不能使用客户端提交的价格。

### 7.2 视频挂商品

- 一个视频可以挂多个商品。
- 一个商品可以被多个作者、多个视频推广。
- 视频和商品之间是“推广关系”，不是“归属关系”。
- 删除视频时，不影响商品；删除商品时，视频仍保留但商品卡失效。

### 7.3 库存

- 库存是交易域内部事实，不直接暴露给 Feed。
- 扣减库存必须原子化，防止超卖。
- 订单取消或超时未支付，需要回补库存。

### 7.4 订单

- 订单金额以服务端计算为准。
- 每个用户对同一商品/活动的重复提交必须幂等。
- 订单状态转换必须走状态机，非法转换直接拒绝。
- 订单创建时记录归因快照，之后不随作者/视频/商品信息变化而改变。

### 7.5 作者带货统计

- 归因口径：以“订单创建/支付成功”时的来源为准。
- 至少支持统计：
  - 订单数
  - 购买人数（去重用户）
  - GMV
  - 按视频维度、按商品维度拆分
- 统计可以异步聚合，但必须能对账。

## 9. 模块边界建议

```text
内容域：
  video / feed / user
    负责视频、作者、商品挂链展示

交易域：
  product / inventory / order / payment
    负责商品、库存、订单、支付

归因 / 统计域：
  attribution / analytics
    负责作者带货数据、转化漏斗、对账
```

边界原则：

- `feed` 不直接依赖 `inventory` / `order`
- `order` 不依赖 `video` 的业务逻辑，只保存来源 ID
- 作者统计不直接跨模块调用，使用只读模型或事件聚合
- 跨域接口优先使用 ID / DTO，不共享内部 model

## 10. 验收标准

Commerce v1 完成时，应满足：

1. 作者发布视频时可以挂商品，Feed 能展示商品卡。
2. 用户点击商品卡能进入商品详情并下单。
3. 重复提交订单不会产生多个订单。
4. 并发下单不会超卖。
5. 订单状态机所有合法/非法转换有测试覆盖。
6. 相同模拟支付事实重复提交不会改变订单结果；不能将用户命令伪装为渠道回调。
7. 订单超时未支付能自动关闭并回补库存。
8. 系统能按作者统计订单数、购买人数和 GMV。
9. 所有新增接口有 OpenAPI 契约，并通过 route-sync 测试。
10. 作者不等于商家的角色模型在文档和代码命名中保持一致。

## 11. 与现有 Feed 系统的关系

- Feed 继续只负责“内容”，不负责交易。
- 商品卡是 Feed 与 Commerce 的衔接点。
- 现有 `product_ids` 字段可以保留，但 Commerce 落地后应补充商品卡 DTO 聚合。
- 点击商品卡可先记录事件，后续用于转化漏斗。

## 12. 面试 / 演示叙事

如果向面试官介绍这个项目，可以这样讲：

1. 这是一个内容电商平台，不是单纯 Feed 或单纯商城。
2. 作者是内容创作者和带货渠道，不是商家。
3. 系统核心难点是内容域和交易域的耦合控制。
4. 我们通过“视频-商品关联表 + 订单归因快照 + 作者统计只读模型”来解耦。
5. 秒杀和 Kafka 不是一上来就引入的，而是等普通交易闭环稳定后，用压测数据驱动引入。
