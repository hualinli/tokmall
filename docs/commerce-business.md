# 商城业务梳理（Product / Business View）

> 本文档区分 Commerce v1 已交付范围与后续产品设想。当前接口与状态以
> [`OpenAPI`](../internal/api/openapi.yaml) 和 [`Commerce v1 技术实现`](commerce-v1-technical-design.md) 为准。

## 1. 业务定位

TokMall 不是“另一个电商平台”，而是**短视频内容电商**：

- 用户因为内容（视频）产生购买动机
- 作者是内容创作者 / 带货推广者，不一定是商家
- 商家 / 平台拥有商品、库存和订单
- 系统需要回答：“这个作者带来了多少交易？”

一句话：**内容是流量入口，交易是转化终点，作者是归因渠道。**

## 2. 核心角色

| 角色 | 说明 | 关键诉求 |
|---|---|---|
| 普通用户 | 浏览 Feed、看视频、点赞关注、点击商品、下单 | 看到感兴趣的商品，购买流程顺畅，能查订单 |
| 作者 / 创作者 | 发布视频，在视频中挂商品链接，帮商家带货 | 能选择可推广商品，查看自己带来的订单/人数/佣金 |
| 商家 / 平台 | 创建商品、管理库存、处理订单、创建秒杀活动 | 商品可售、不超卖、订单状态准确、能结算 |
| 平台运营 | 审核内容、管理活动、查看转化漏斗 | 内容合规、活动可控、数据可分析 |

> 重要区分：**作者不等于商家。**
> 作者是“推广渠道”，商家是“商品所有者”。Commerce v1 为避免缺少推广授权时越权挂货，
> **仅允许作者推广自己创建的在售商品**；跨商家带货与一个商品由多位作者推广属于后续授权模型。

## 3. 核心业务目标

1. 让用户能在视频场景里完成“看到 -> 感兴趣 -> 购买”的闭环。
2. 让作者看到自己的成交效果；佣金和收益结算留待后续版本。
3. 让商家/平台能安全地管理库存和订单，不超卖、不重复下单。
4. 让系统能准确归因每一笔订单来自哪个作者/视频，用于结算和运营分析。

## 4. 核心用户故事

### 4.1 普通用户

- 我在 Feed 里刷到一条视频，视频下方有商品卡。
- 我点击商品卡，能进入商品详情页。
- 我下单时，系统能记住我是从哪个作者的哪个视频点进来的。
- 我可以在订单列表看到自己的订单状态。
- 我可以对未支付订单取消，对已支付订单申请售后（后续版本）。

### 4.2 作者 / 创作者

- 我发布视频时，可以从可推广商品列表中选择商品挂到视频上。
- 我可以看到自己的已支付订单数、去重购买人数和 GMV；接口还返回按商品/视频拆分，前端目前只展示总计。曝光、点击留待后续。
- 我不需要管理库存和发货，只关心推广效果和佣金。
- 我下架某个商品后，之前发布的视频仍然存在，但商品卡变为不可购买。

### 4.3 商家 / 平台

- 我创建商品和 SKU，设置价格、库存和上下架状态。
- 我可以查看自己商品产生的订单，并对已支付订单执行模拟发货。
- 我可以创建秒杀活动，设置活动库存和活动时间。
- 我需要防止超卖、重复下单和恶意刷单。

### 4.4 平台运营

- 我可以看到“视频 -> 商品点击 -> 下单 -> 支付”的转化漏斗。
- 我可以按作者、按视频、按商品维度分析带货效果。
- 我可以审核商品和内容。

## 5. 核心业务流程

### 5.1 视频带货闭环

```text
商家创建商品 / SKU / 库存
        ↓
作者发布视频，选择要挂的商品
        ↓
Feed / 视频详情展示商品卡
        ↓
用户点击商品卡
        ↓
进入商品详情页
        ↓
下单 -> 模拟支付 -> 商家模拟发货 -> 买家确认完成
        ↓
系统记录订单归因（作者、视频、商品）
        ↓
作者带货中心展示数据
```

### 5.2 普通下单流程

```text
用户提交订单
  -> 服务端校验商品状态
  -> 服务端重新读取价格，不信任客户端价格
  -> 原子扣减库存
  -> 创建订单（状态：PENDING_PAYMENT）
  -> 用户支付（模拟支付）
  -> 订单变为 PAID
  -> 商家模拟发货（FULFILLING）-> 买家确认完成（COMPLETED）
```

### 5.3 秒杀流程（后续版本）

```text
活动开始前：展示活动商品和倒计时
活动开始：用户点击秒杀
  -> 限流
  -> 资格校验
  -> Redis 预扣 / 数据库条件扣减
  -> 创建订单
  -> 异步削峰（Kafka / Worker，按需引入）
  -> 超时未支付回补库存
```

## 6. 功能范围

### Commerce v1（当前分支已实现；远端 `main` 尚缺订单收尾提交）

- 商品：商品列表、商品详情、上下架
- SKU：规格、价格、库存
- 普通下单：创建订单、订单详情、订单列表
- 模拟支付：受 JWT 保护的买家模拟支付命令、重复请求幂等（真实渠道回调另设适配器）
- 订单状态机：待支付 -> 已支付 -> 发货中 -> 完成；待支付可取消/超时关闭
- 视频挂商品：视频与商品关联，Feed/视频详情返回商品卡
- 订单归因：记录 `author_id` / `video_id` / `product_id`
- 作者带货数据：按作者统计订单数、购买人数、GMV

以上“发货”和“完成”是学习环境的状态流转，没有真实物流接口；商品推广当前只支持作者挂自己的在售商品。

### Commerce v2（后续再做）

- 秒杀活动
- 购物车
- 优惠券
- 售后 / 退款
- 佣金结算
- 多商家 / 店铺
- 复杂营销归因（多触点归因）
- 跨商家推广授权；曝光与点击漏斗

### 明确不做

- 真实支付渠道
- 复杂税率 / 多币种
- 真实物流
- 开放平台 / 商家后台完整权限体系
- 一开始就上 Kafka / 微服务

## 7. 关键业务规则

### 7.1 商品

- 商品属于商家/平台，不属于作者。
- 商品下架后，已挂载的视频仍可展示，但商品卡应显示“已下架/不可购买”。
- 下单时必须重新读取商品最新价格和状态，不能使用客户端提交的价格。

### 7.2 视频挂商品

- 一个视频可以挂多个商品。
- 当前仅能挂作者自己创建的在售商品；跨作者/跨商家的推广关系待授权模型上线。
- 同一个已发布视频最多有 5 个有效商品挂载。
- 视频和商品之间是“推广关系”，不是“归属关系”。
- 删除视频时，不影响商品；删除商品时，视频仍保留但商品卡失效。

### 7.3 库存

- 库存是交易域内部事实，不直接暴露给 Feed。
- 扣减库存必须原子化，防止超卖。
- 订单取消或超时未支付，需要回补库存。

### 7.4 订单

- 订单金额以服务端计算为准。
- 同一用户使用相同幂等键和相同请求载荷重试，只创建一单、扣减一次；同键不同载荷返回冲突。
- 订单状态转换必须走状态机，非法转换直接拒绝。
- 订单创建时记录归因快照，之后不随作者/视频/商品信息变化而改变。

### 7.5 作者带货统计

- 归因来源在订单创建时冻结；当前统计只计算已支付及之后履约状态的订单。
- Commerce v1 已支持：
  - 订单数
  - 购买人数（去重用户）
  - GMV
- 接口还支持按视频/商品拆分的成交统计；曝光/点击转化和佣金尚未实现。
- 当前从订单事实实时聚合，未使用异步统计表。

## 8. 当前数据模型

商家与作者目前都是 `users` 中的用户，**没有单独的 `merchants` 表**。商品价格在 `skus`，库存数量在单独的 `inventory` 表；库存变化写 `inventory_transactions`。视频推广关系在 `video_products`，订单与支付事实在 `orders`、`order_items`、`payments`。

订单中的 `source_video_id`、`source_author_id`、`source_product_id` 是下单来源快照；订单项保存标题、规格、单价等成交快照。作者统计实时查询这些订单事实，**没有 `author_sales_stats` 聚合表**。准确字段、约束和索引见 [`000007`～`000014` 迁移](../migrations/)；关系解释见 [Commerce v1 技术实现](commerce-v1-technical-design.md)。

## 9. 当前模块边界

- 内容域：`video` 管理视频和播放事件，`feed` 查询内容并装配商品卡。
- 交易域：`product` 管理商品/SKU，`inventory` 管理商家调库存，`order` 在同库事务内创建订单与条件扣减/回补库存，支付事实也由 `order` 管理。
- 推广与归因：`promotion` 管理视频商品关系；`attribution` 只读已支付订单，给作者提供总计和视频/商品拆分。

Feed 不修改库存或订单；订单只保留来源 ID 快照，不依赖视频模块的 Go 类型。更完整的依赖图见 [后端架构](backend-architecture.md)。

## 10. Commerce v1 验收标准

当前工作分支已实现以下范围；真实渠道支付、物流和跨商家推广不在这组验收内：

1. 作者发布视频时可以挂商品，Feed 能展示商品卡。
2. 用户点击商品卡能进入商品详情并下单。
3. 重复提交订单不会产生多个订单。
4. 并发下单不会超卖。
5. 订单状态机所有合法/非法转换有测试覆盖。
6. 相同模拟支付事实重复提交不会改变订单结果；不能将用户命令伪装为渠道回调。
7. 订单超时未支付能自动关闭并回补库存。
8. 系统能按作者统计订单数、购买人数和 GMV。
9. 所有新增接口有 OpenAPI 契约，并通过 route-sync 测试。
10. 作者不等于商家的角色模型在文档和代码命名中保持一致。

## 11. 与现有 Feed 系统的关系

- Feed 继续只负责“内容”，不负责交易。
- 商品卡是 Feed 与 Commerce 的衔接点。
- 当前 Feed 与视频详情已返回商品卡 DTO；商品下架后卡片保留并显示不可购买。
- 商品卡点击事件尚未单独持久化，后续可用于转化漏斗。

## 12. 面试 / 演示叙事

如果向面试官介绍这个项目，可以这样讲：

1. 这是一个内容电商平台，不是单纯 Feed 或单纯商城。
2. 作者是内容创作者和带货渠道，不是商家。
3. 系统核心难点是内容域和交易域的耦合控制。
4. 我们通过“视频-商品关联表 + 订单归因快照 + 作者统计只读模型”来解耦。
5. 秒杀和 Kafka 不是一上来就引入的，而是等普通交易闭环稳定后，用压测数据驱动引入。
