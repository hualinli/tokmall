# 支付成功与用户取消：如何只产生一个订单终态

## 解决的问题

待支付订单可能同时收到支付平台的成功回调和用户取消请求。如果两条路径只是分别执行
`UPDATE orders SET status = ...`，就可能出现支付记录已经成功、订单却显示已取消，或者取消
回补库存后订单又被晚到回调改成已支付。

本阶段只实现同步的模拟支付成功与用户主动取消，不包含 HTTP 契约、退款和超时关单 Worker。

## 核心不变量

1. `PENDING_PAYMENT` 只能进入 `PAID`、`CANCELED` 或后续的 `EXPIRED`，终态不能互相跳转。
2. 成功支付记录、订单 `PAID + paid_at` 必须在同一事务提交。
3. 订单取消、库存回补、`ORDER_CANCELED` 流水必须在同一事务提交。
4. 一笔订单最多有一个竞争路径赢得 `PENDING_PAYMENT`，取消最多回补一次。
5. 支付金额只与服务端订单快照金额比较，不能相信回调方用商品现价重算的金额。
6. 同一 `payment_no + provider_trade_no`、同订单、同金额的成功回调可以安全重放；任一业务事实变化都返回幂等冲突。

## 为什么使用订单行锁

支付和取消都在事务开始时通过 `SELECT ... FOR UPDATE` 锁定同一订单行，随后才读取当前状态并
执行副作用。订单行因此成为这两条路径共同的串行化点：

- 支付先拿锁：写入 SUCCESS payment，再把订单从 PENDING_PAYMENT 改为 PAID；取消随后看到
  PAID，只返回状态冲突，不回补库存。
- 取消先拿锁：把订单改为 CANCELED、回补库存并写流水；支付随后看到 CANCELED，只返回状态
  冲突，不写成功支付。

状态更新仍带 `WHERE status = 'PENDING_PAYMENT'`。行锁负责把多步事务串行化，条件更新则是第二道
防线，防止以后重构时遗漏来源状态检查。

这里没有使用 Redis 分布式锁。真正需要原子提交的数据都在 PostgreSQL 中，数据库行锁比外部锁
少一个故障协调点，也不会产生“Redis 锁过期但数据库事务还没结束”的双写窗口。

## 支付回调幂等

回调先锁订单，再按内部 `payment_no` 或支付渠道 `provider_trade_no` 查找已有记录：

- 两个标识、订单 ID、金额、SUCCESS 状态全部一致：返回原支付结果，标记为 replay；
- 找到记录但业务事实不同：返回幂等冲突；
- 没有记录且订单仍待支付：核验服务端订单金额，写 SUCCESS payment 并更新订单；
- 订单已取消或进入其他终态：返回状态冲突，晚到支付不能复活订单。

数据库已有 `payment_no` 唯一约束和非空 `provider_trade_no` 部分唯一索引，它们负责跨订单并发时
的最终仲裁。服务层校验与数据库唯一约束分别解决请求语义和并发落库，不能互相替代。

## 取消为什么不会二次回补

取消拿到订单锁后，只有 `PENDING_PAYMENT` 才执行以下三步：

1. 条件更新为 `CANCELED` 并写 `canceled_at`；
2. 按订单项数量增加库存，同时递增库存版本；
3. 写 `ORDER_CANCELED` 库存流水，业务键使用订单号。

三步在同一事务内，任何一步失败都会整体回滚。后续重复取消在拿锁后直接看到 CANCELED，返回
同一业务结果而不再次修改库存。数据库的 `(sku_id, reason, biz_id)` 唯一约束仍保留为流水层的
最后防线。

## 锁顺序与死锁边界

本阶段所有订单终态迁移都先锁订单，再触碰支付或库存；取消的顺序固定为：

```text
orders -> order_items(read) -> inventory -> inventory_transactions
```

后续超时关单也必须沿用相同顺序。若另一条业务路径反向先锁库存再锁订单，会形成死锁环，因此
新增订单终态路径时需要审查锁顺序，而不能只审查单条 SQL。

## 测试证据

真实 PostgreSQL 集成测试覆盖：

- 支付与取消同时开始，只有一个请求成功，另一个收到状态冲突；
- 50 个并发取消只产生一条取消流水，只回补一次；
- 50 个相同支付回调只产生一条 SUCCESS payment；
- 取消完成后的晚到支付不能把订单改回 PAID；
- 相同外部交易号但变更支付号的重放返回幂等冲突；
- 非订单本人取消统一返回订单不存在，且不改变状态或库存；
- 每种终态都同时核对订单、支付数、库存余额、两类库存流水数量和流水净和。

## 当前边界

- 当前是模拟支付成功入口，没有验签、证书轮换、渠道主动查单和退款；真实支付接入时这些是前置条件。
- 若订单到期但超时 Worker 尚未锁定它，支付仍可能先赢得竞争。这是“谁先获得订单锁谁生效”的明确
  语义；下一阶段 Worker 会使用同一状态机与锁顺序。
- 当前订单只有一个 SKU，因此取消可直接按唯一订单项回补；多商品、拆单或部分退款需要新的履约与
  退款模型，不能复用本阶段的简单取消语义。
- 支付和取消 HTTP handler、OpenAPI 错误映射属于下一交付，不在本模块混入。
