# 生产配置校验：为什么服务宁可拒绝启动

## 解决的业务问题

原实现混用了两类需求：本地开发希望 PostgreSQL、Redis、MinIO 开箱即用，生产部署却不能接受默认密码、关闭 TLS 或短签名密钥。更隐蔽的问题是，显式写错布尔值、整数或时长时，程序会静默采用默认值。运维人员以为配置已经生效，服务实际运行在另一套参数上，这类“配置漂移”比启动失败更难发现。

本次引入显式的 `APP_ENV` 边界：必须明确设置为 `development` 或 `production`，避免生产部署漏配环境标识后悄悄降级为开发规则。开发环境保留本地默认值；生产配置不满足最低安全基线时，服务在连接数据库、Redis 和对象存储之前直接返回错误。

## 为什么采用启动时 fail-fast

配置错误不是可重试的运行时故障。让进程带着错误配置继续服务，会把问题推迟到签发弱 JWT、生成不可验证游标、写入错误数据库或通过明文链路传输之后。启动失败能让容器编排系统明确标记部署失败，也使错误最靠近根因。

校验分两层：

1. 所有环境都校验类型和值域。只要调用方显式提供了非法整数、时长或布尔值，就返回指出变量名和期望类型的错误，不再静默回退。
2. 生产环境额外要求关键依赖配置全部显式提供，并拒绝短 JWT/游标签名密钥、复用两个签名密钥、开发默认凭据，以及数据库、MinIO 或 Redis 禁用 TLS。

错误只包含变量名和规则，不回显变量值。启动脚本也不再把 `JWT_SECRET` 打印到终端，避免密钥进入 CI 日志、shell 录屏或故障工单。

## 核心不变量

- `development` 可以使用仓库定义的本地依赖默认值；`production` 不能继承关键依赖默认值。
- JWT 与 Feed 游标使用不同的签名密钥，且生产密钥至少 32 个字符。
- 生产数据库、Redis 和对象存储链路必须启用 TLS；Redis 客户端最低接受 TLS 1.2。
- Redis 在生产必须显式配置认证密码。
- 正数 TTL、有效端口、非负 Redis DB，以及启用限流时为正的配额，在任何环境都成立。
- 配置错误信息和正常启动日志都不包含密钥内容。

## 并发、重试与部分失败

配置在进程启动时读取一次，完成校验后作为不可变值注入各模块，因此不存在请求并发修改配置的问题。配置校验失败时尚未建立外部连接，也没有部分初始化需要补偿。重启只有在部署方修正环境变量后才有意义；盲目重试不会把错误配置变正确。

外部依赖在校验通过后仍可能连接失败，那属于另一层启动错误，由数据库、Redis 或 MinIO 初始化逻辑报告。配置校验不伪装成健康检查，也不替代运行期 readiness。

## 为什么没有引入配置中心

当前是单体学习项目，配置数量和实例规模都不足以证明引入配置中心、动态刷新或密钥轮换控制面的成本。环境变量符合容器部署习惯，也能由 Kubernetes Secret、云 Secret Manager 等平台在进程外管理。这里先保证“输入有边界、错误可定位、秘密不泄露”，而不是搭建尚无消费场景的基础设施。

## 当前边界与后续演进

- 字符长度只能过滤明显弱密钥，不能测量真实熵；生产密钥仍应由密码学安全随机源生成。
- 当前只区分开发与生产，没有单独的 staging 策略。预发布若承载真实数据，应直接使用 `production` 校验。
- `.env.production.example` 只是变量清单，包含不可用占位符；真实秘密不得提交到 Git。
- 后续若需要密钥轮换，应为 JWT 增加 key id 和多密钥验签窗口，而不是在线覆写当前进程内配置。

面试时可以概括为：**开发默认值优化反馈速度，生产 fail-fast 守住安全下限；二者由显式环境边界隔离，而不是寄希望于部署人员永不犯错。**
