# Commerce v1：订单查询与履约收尾

## 查询为什么按身份分两套入口

买家只能按 `orders.user_id` 查看自己的订单；商家只能按 `orders.merchant_id` 查看卖出的订单。查询条件直接进入 SQL，详情对不存在与非本人统一返回 404。不能先按订单 ID 读出记录再让 Handler 判断，否则很容易在列表、详情或后续扩展中漏掉权限条件。

订单项使用下单时保存的标题、规格、价格快照，不回查可能已经改名或下架的商品。列表按订单 ID 倒序，`before_id` 表示上一页最后一条；先取 `limit+1` 条判断是否有下一页，再批量读订单项，避免逐笔 N+1 查询。

## 履约状态为什么由不同参与者推进

商家只能把自己的 `PAID` 订单推进到 `FULFILLING`，代表学习环境中的模拟发货；买家只能把自己的 `FULFILLING` 订单推进到 `COMPLETED`，代表确认收货。两个命令都先以所有权条件 `FOR UPDATE` 锁住订单，再按状态条件更新；并发重试只有第一次写入，后续返回 `replayed=true`。不能让买家自行标记发货，也不能让商家替买家确认收货。

新增的 `fulfilling_at` 和 `completed_at` 由数据库 CHECK 约束与状态绑定，防止出现“已完成但没有完成时间”的半状态。支付后只推进订单状态，不回补库存；取消与超时关闭仍只允许在待支付阶段回补。

## 模拟支付的边界

目前的支付是受 JWT 保护的买家模拟命令，重复支付事实由 `payment_no`、`provider_trade_no` 和订单金额共同判定幂等。它不承担真实渠道回调入口的角色。真实接入时必须另建渠道适配器，先验签、校验时间窗、商户和金额，再将可信的支付事实送入领域服务；详见 [支付 / 取消 API 的安全边界](payment-cancel-api-security.md)。

## 验证证据

- 真实 PostgreSQL 隔离 schema：买家和商家读权限、订单分页、履约非法转换、并发发货仅一次、完成后库存不回补。
- Go 全量测试与 `internal/order`、`cmd/api` race 测试通过；OpenAPI route-sync 通过。
- Playwright 完整交易链路覆盖买家订单详情、商家发货、买家确认完成及作者统计。
