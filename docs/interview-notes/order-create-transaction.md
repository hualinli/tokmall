# 创建订单事务：幂等、防超卖与失败回滚

## 1. 解决的业务问题

创建订单不是依次调用“查商品、减库存、写订单”三个接口。网络重试和并发请求会导致重复订单、重复扣库存；中途任一步失败还可能留下半订单。当前 Commerce v1 只支持单 SKU，把创建订单、订单项快照、库存扣减和库存流水放进一个 PostgreSQL 本地事务，先把最重要的一致性闭环做实。

客户端只提交 `user_id`、`sku_id`、购买数量、幂等键和可选的完整来源三元组。价格、商品标题、规格和商家都从数据库读取，客户端不能指定成交价。

## 2. 事务顺序

新请求在一个事务内执行：

1. 检查该用户和幂等键是否已有订单；有则比较请求指纹并返回历史结果；
2. 用 `FOR SHARE` 读取在售商品和启用 SKU，取得服务端价格及快照；
3. 若携带来源，锁定并校验 `ACTIVE` 的 `video_products` 关系，且来源商品必须是 SKU 所属商品；
4. 计算 `单价 × 数量`，显式检查 `int64` 溢出；
5. 以 `(user_id, idempotency_key)` 唯一约束插入订单，完成并发幂等 claim；
6. 执行 `UPDATE inventory SET quantity=quantity-? WHERE sku_id=? AND quantity>=?`；
7. 写 `ORDER_CREATED` 库存流水；
8. 写订单项成交快照；
9. 一起提交。任何一步失败，订单 claim、库存和流水全部回滚。

先查历史订单有一个容易忽略的原因：首单后商品可能下架，但同 key 重试仍应返回原订单，不能重新按当前商品状态失败。这个快速路径只改善已提交重放；两个并发首次请求都没查到时，最终仍由数据库唯一约束仲裁。

## 3. 并发幂等为什么成立

幂等键按用户隔离，不同用户可以使用相同 key。系统把 `user_id`、`sku_id`、数量和来源三元组序列化为固定结构，再保存 SHA-256 指纹：

- 同 key、同指纹：返回原订单和原订单项，不再扣库存；
- 同 key、不同指纹：返回幂等冲突；
- 两个并发首次请求：都可能通过前置读取，但只能有一个插入唯一键；另一个 INSERT 会等待胜出事务提交或回滚。胜出者提交后，后来者读取并返回原订单；胜出者回滚后，后来者可以继续创建。

这也是为什么不能只在应用内用 map 或 Redis `SETNX`：应用锁跨实例失效；Redis claim 与 PostgreSQL 交易数据之间还会新增双写一致性问题。订单事实最终存放在 PostgreSQL，就让同一个数据库事务和唯一约束做仲裁。

## 4. 防超卖为什么不是“先查再减”

`SELECT quantity` 后在 Go 中判断再 UPDATE 存在检查与写入之间的竞争窗口。这里把条件放进一条原子 UPDATE。PostgreSQL 修改同一库存行时会串行获取行锁，后到事务在锁等待后会基于最新版本重新判断 `quantity >= requested`；受影响行数为 0 就是库存不足。因此库存不会变成负数。

商品/SKU 和来源关系使用共享锁，是为了让“在售校验”和并发下架/禁用之间有清晰顺序。共享锁不会互相阻塞多个买家读取，但会让状态 UPDATE 等当前创建事务结束。库存热点仍会集中在单个 SKU 行上，这是数据库直扣方案有意保留、后续用真实压测判断的容量边界。

## 5. 关键不变量与失败语义

- 价格只能来自服务端，订单和订单项金额相同；金额使用分，禁止浮点数；
- 数量范围为 1 到 1000，避免异常请求制造超大金额或锁持有；
- 来源字段要么全无，要么完整，且必须命中活动挂载关系；
- 一笔新订单恰好有一个订单项、一次负向库存变更和一条 `ORDER_CREATED` 流水；
- 流水的 `order_id` 与订单关联，`biz_id` 使用唯一订单号，符合现有 `(sku_id, reason, biz_id)` 复合幂等约束；
- 库存行缺失不是“库存不足”，而是 SKU 创建不变量被破坏，应作为系统错误暴露；
- 商品/SKU 不可售和来源无效统一表现为不可下单，不泄露内部状态细节。

事务中任何 INSERT 或 UPDATE 失败都会回滚，因而不会出现“库存已扣但没有订单项”或“订单已建但没有流水”。当前单元测试覆盖参数边界、指纹稳定性与冲突、金额溢出和关键 SQL 约束；真实 PostgreSQL 的 500 并发/100 库存实验留在 1C，与 API 接入一起验证锁等待、提交可见性和最终对账。

## 6. 为什么暂时不上 Redis 和 MQ

Redis 预扣适合数据库库存热点已经成为可测量瓶颈的场景，但会引入预扣失败补偿、缓存与数据库对账、消息丢失和异步下单反馈。当前普通订单首先需要证明正确性，PostgreSQL 条件更新足够清楚，也便于用一份事务日志恢复。

MQ 也不能替代创建订单的原子事务：若先发消息再写订单会有幽灵消息，先写订单再发消息会丢事件。项目计划在支付成功后引入 Transactional Outbox，把可靠分发用于统计等非核心副作用；它不是防超卖的前置条件。

## 7. 当前边界和演进

当前只支持单 SKU、单商家、人民币分，不含优惠、运费、税费、购物车或拆单。库存行是热点时，先用 1C 的真实数据库实验记录吞吐和锁等待；只有证据表明数据库直扣不满足目标，再演进入口限流、Redis Lua 预扣和异步排队。面试中应诚实描述为“正确的普通订单基线和可演进边界”，不能把它包装成已经承载大促流量的秒杀系统。
