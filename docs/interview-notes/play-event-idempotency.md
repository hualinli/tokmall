# 播放事件幂等：为什么“唯一键去重”还不够

## 结论

`POST /videos/{id}/play` 是同步落库版播放上报。客户端为每一次播放生成一个
`event_id`，服务端把它作为事件事实的唯一身份：

- 首次上报插入一条 `play_events` 事实；
- 同一个 `event_id`、同一组业务载荷重试，返回成功但不重复计数；
- 同一个 `event_id` 被另一个用户、另一个视频或不同关键字段复用，返回
  `409 IDEMPOTENCY_CONFLICT`；
- 非法 UUID 在 service 边界返回 `400 INVALID_ARGUMENT`，不会让 PostgreSQL
  负责解析并最终暴露成 500。

这里的“幂等”不是看到唯一键冲突就忽略错误，而是验证重试请求是否仍然描述
同一个业务事实。

## 为什么不只写 `ON CONFLICT DO NOTHING`

下面的实现虽然能避免重复插入，但会把恶意或编程错误隐藏掉：

```sql
INSERT INTO play_events(event_id, user_id, video_id, ...)
VALUES (...)
ON CONFLICT (event_id) DO NOTHING;
-- 无论冲突行的 user_id/video_id 是否相同，都返回 204
```

例如，用户 A 上报视频 10 使用 `event_id=e`，用户 B 又用 `e` 上报视频 99。
如果只吞掉唯一冲突，第二个请求看起来成功，但调用方误以为视频 99 已被记录，
而数据库实际保留的是视频 10。更危险的是，客户端 bug 或攻击者可以借此制造
“假成功”。

因此 repository 返回两种事实：

```text
RowsAffected = 1  → 本次插入成功
RowsAffected = 0  → 唯一键冲突，读取 event_id 已存在的完整事实
```

service 再比较用户、视频、session 和客户端时间等业务字段。`trace_id` 是
HTTP 请求级观测元数据，重试时本来就可能不同，不纳入业务事实比较；`created_at`
也是数据库入库事实，同样不参与比较。

## UUID 版本决策

迁移中的 `event_id` 类型是 PostgreSQL `UUID`，它没有限制 UUID version；当前 Web
客户端调用 `crypto.randomUUID()`，生成的是 v4，而历史设计文档曾写过 v7。因此
本阶段接受标准的 canonical UUID 文本，v4/v7 都合法，不凭空增加“只能 v7”的
限制。v7 将来可以带来按生成时间近似有序的好处，但它不是本端幂等正确性的前提。

入口仍做严格文本校验：只接受 36 字符、带短横线的标准形式（大小写均可），拒绝
URN、无短横线、大括号、空值和 nil UUID，并统一存成小写 canonical 形式。这样
数据库 UUID 的等价规则不会让 API 出现多套文本身份。

## `played_at` 的精度与缺省值

Go `time.Time` 可以携带纳秒，但 PostgreSQL `TIMESTAMPTZ` 只保存微秒。若第一次
请求带有 `...123456789`，直接插入后数据库只剩微秒，再用原请求重放并拿 Go 时间
做纳秒级比较，就会错误地返回幂等冲突。

所以 service 入口把时间转成 UTC 并截断到微秒，插入和比较使用同一个精度。

`played_at` 还可以省略。省略时服务端补接收时间，但每次 HTTP 重试的接收时间
天然不同，不应该因为这个派生字段变化而失败。迁移增加了
`played_at_provided`：

- `false`：客户端没有提供时间，服务端补的时间是入库元数据，不参与重放比较；
- `true`：客户端明确提供时间，必须按微秒精度一致；
- 显式提供与省略是两种不同载荷，不能互相冒充。

## 并发边界

幂等判断不能采用“先查是否存在，再插入”：

```text
请求 A：SELECT 不存在
请求 B：SELECT 不存在
请求 A：INSERT
请求 B：INSERT  -- 竞争窗口，唯一键冲突
```

真正的仲裁者必须是数据库唯一索引。当前实现让 PostgreSQL 处理并发：竞争者在
唯一索引上等待先到请求完成，随后 `ON CONFLICT DO NOTHING` 返回 0 行，再读取
已提交的事实。这样即使 32 个相同请求同时到达，也只会落一条记录；每个重试者
都会比较同一条已提交事实并成功返回。

若冲突后反而读不到事实，这是数据库事务或数据生命周期异常，不是“幂等成功”，
服务端按内部错误处理，避免静默丢失事件。

## 错误分层

分层职责保持单向：

1. repository 把 `gorm.ErrRecordNotFound`、可识别的 PostgreSQL 外键错误翻译为
   video 领域哨兵，并返回 INSERT 是否真正创建事实；
2. service 负责业务判断：视频必须是 `PUBLISHED`，UUID 和时间参数合法；相同事实
   成功，不同事实返回 `ErrIdempotencyConflict`；
3. handler 把参数错误映射为 400，把资源不可见映射为 404，把幂等键冲突映射为
   409，其余未知错误统一 500。

业务冲突不是系统故障，不应该打 Error 日志；实现用 Warn 记录 event_id、用户和
视频，既能排查调用方 bug，又不把正常的冲突流量伪装成基础设施故障。

## 面试时可以这样回答

**问：为什么不用 Redis 做去重？**

播放事件的权威事实最终在 PostgreSQL，且当前同步版本量级尚未证明需要引入
Kafka/Redis。数据库唯一约束能在多实例并发下提供最终仲裁；Redis 可以做前置降载，
但不能替代持久化事实，否则还要处理 Redis 丢失、数据库写失败和双写不一致。

**问：`event_id` 冲突后为什么还要查一次？**

因为唯一键只说明“身份相同”，不说明业务载荷相同。查出已有事实后比较关键字段，
才能区分网络重试和幂等键误用；前者 204，后者 409。

**问：并发下会不会两次成功？**

相同 event_id 只有一个 INSERT 能影响一行，其他请求由唯一索引仲裁后读取胜者事实。
它们可以都得到业务层“成功”（因为是同一个事实的重试），但数据库不会出现两条事件，
因此播放计数不会重复增加。

**问：为什么不强制 UUID v7？**

当前浏览器客户端生成 v4，数据库 UUID 类型也没有 version 约束；v7 是排序优化
选项，不是幂等必需条件。协议先接受 v4/v7，若未来需要按事件时间做高效范围扫描，
再单独增加客户端能力、版本约束或索引设计。

## 当前边界

这是同步写入版，接口成功意味着原始事件已经提交数据库。若以后播放写入成为独立
瓶颈，再演进到 Kafka：接口先校验并投递，consumer 仍必须复用 event_id 唯一约束和
同载荷校验。至少一次投递意味着重复消息是正常情况，不能把“换成 MQ”误认为已经
自动获得 exactly-once。
