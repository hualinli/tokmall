# 订单超时关单 Worker：多实例安全与支付竞争

## 解决的业务问题

创建订单时库存已经扣减，但用户可能一直不支付。如果待支付订单永久占用库存，商品会出现“数据库有货、业务不可售”的假售罄。因此后台 Worker 会扫描 `expires_at <= now` 的 `PENDING_PAYMENT` 订单，将其迁移为 `EXPIRED`，同时回补库存并写入 `ORDER_EXPIRED` 流水。

核心不变量是：一笔订单只能从 `PENDING_PAYMENT` 进入一个终态；只有真正进入 `EXPIRED` 的事务才能回补一次库存。状态变化、库存回补和流水必须同事务提交或回滚。

## 为什么使用 `FOR UPDATE SKIP LOCKED`

`ExpireNext` 每次按 `(expires_at, id)` 取一笔到期订单，并使用 `FOR UPDATE SKIP LOCKED`：

- `FOR UPDATE` 把订单行变成支付、取消、过期三条路径共同的仲裁点；
- `SKIP LOCKED` 让多个实例不等待同一订单，而是各自领取其他到期订单；
- `(expires_at, id)` 提供稳定顺序，并直接命中 `idx_orders_pending_expiry` 部分索引；
- 未找到记录不是错误，只表示当前没有可领取的到期订单。

如果支付先锁住订单，过期扫描会跳过它，支付提交后该订单不再满足待支付条件。如果过期先锁住订单，支付等待后看到 `EXPIRED`，返回状态冲突。两者不可能同时成功。

## 为什么一单一个短事务

`RunOnce` 最多循环 `batchSize` 次，但 `ExpireNext` 每次只开启一笔订单的事务，锁顺序固定为：

```text
orders -> order_items -> inventory -> inventory_transactions
```

这避免了把一批订单锁在同一长事务中，也避免多 SKU 批次采用不一致锁顺序时产生死锁。一笔订单若存在数据不变量错误，只回滚这一笔；本轮停止并记录错误，下一轮再重试，而不会让服务进程崩溃。

## 重试、幂等与部分失败

订单行锁和来源状态条件更新是主要的“只执行一次”保证。即使同一订单被重复扫描，终态已不是 `PENDING_PAYMENT`，不会再次进入过期事务。库存流水的 `(sku_id, reason,biz_id)` 唯一键是第二道数据库防线；`biz_id` 使用不可变订单号，原因使用 `ORDER_EXPIRED`。

库存更新或流水插入失败时，整个事务回滚，订单仍是待支付、库存也没有被部分回补。下一轮扫描可以安全重试。Worker 启动时先立即跑一轮，随后使用可取消 ticker；数据库暂时错误仅记录日志。进程收到退出信号或 HTTP 服务异常退出时，会取消 Worker 并等待其退出后再继续关闭数据库资源；等待带 30 秒上限，避免异常驱动或网络故障让进程永久卡在停机阶段。

## 配置与运维边界

- `ORDER_EXPIRY_WORKER_ENABLED`：默认开启，可在专用 API 实例关闭；
- `ORDER_EXPIRY_WORKER_INTERVAL`：默认 `5s`；
- `ORDER_EXPIRY_WORKER_BATCH_SIZE`：默认 `100`。

显式非法布尔值、时长、整数，以及非正 interval/batch size 都会启动失败，而不是静默退回默认值。

## 为什么现在不用延迟队列

延迟队列会引入消息可靠投递、重复消费、延迟精度、积压恢复和队列运维等额外问题。当前 PostgreSQL 已经保存订单截止时间，并有待支付部分索引；轮询方案简单、可恢复、多实例安全，且几秒级关单延迟符合普通商城订单的业务要求。

未来只有在订单规模使数据库扫描成为可测量瓶颈，或业务要求更高精度时，才考虑“延迟消息提醒 + 数据库补偿扫描”。即使引入队列，数据库状态机仍应是最终事实来源，不能把消息消费当成唯一关单保证。

## 可证明性

- 单元测试覆盖批次边界、空队列、取消及时退出和数据库错误后下一轮重试；
- DryRun 测试固定 `PENDING_PAYMENT + expires_at + ORDER BY + FOR UPDATE SKIP LOCKED` 查询形状；
- 真实 PostgreSQL 测试用四个 Worker 并发处理二十笔到期订单，验证每单只过期一次、库存只回补一次；
- 真实 PostgreSQL 测试让支付和过期并发竞争，验证最终只能是 `PAID` 或 `EXPIRED`，库存和流水与终态一致。
