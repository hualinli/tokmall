# 商品卡与带货统计：读模型保持实时，交易事实保持可对账

## 业务链路

作者给已发布视频挂自己的在售商品。Feed 和视频详情展示商品卡；用户进入商品详情后选择 SKU，创建订单并模拟支付。订单创建时保存视频、作者、商品三个来源 ID，支付成功后作者本人可查看订单数、购买人数、销量和 GMV。

当前“作者只能挂自己的商品”是缺少推广授权体系时的 v1 安全收口，不代表作者与商家在长期模型中是同一角色。

## 为什么商品卡在缓存之后装配

Feed 首页缓存保存视频分页结果。商品卡在每次请求中用一条按页 `video_id IN (...)` 查询装配，并在响应时签发封面 URL。这样挂载、取消挂载或商品下架后，不需要清除全局首页缓存和每位关注者的缓存；下一次请求就读取当前推广关系。下架商品仍显示卡片与“不可购买”状态，删除商品不展示；没有启用 SKU 的卡片最低价为 0。每页最多 100 个视频、每视频最多 5 个启用商品。商品卡不包含库存，最终可购买性仍由创建订单事务校验。

Feed 和 video 各自持有自己的最小商品卡 read model，跨模块不传 ORM model。首次命中缓存后会复制结果和切片，再填充点赞数与商品卡，避免并发请求修改共享数据。商品卡读库失败时请求返回错误，避免把内容中的购买入口错误地展示为“没有商品”。

## 成交归因口径

仅统计 `paid_at` 非空、状态为 `PAID`/`FULFILLING`/`COMPLETED`、且 `source_author_id` 匹配的订单。取消或超时订单不计入；推广关系后来停用、视频删除或商品改价，不改变历史订单快照。订单数按订单计、购买人数按 `user_id` 去重、销量按订单项数量求和、GMV 按订单实付总额求和，金额单位为分。视频和商品维度使用创建订单时保存的来源 ID。

三个聚合查询在 PostgreSQL `REPEATABLE READ READ ONLY` 事务中执行，保证总览与分项看到同一个已提交快照。现阶段直接从订单事实实时聚合，结果可对账；当数据量或查询成本实际成为问题时，再用 Outbox 事件驱动幂等统计投影。`GET /authors/{id}/sales` 只允许作者本人访问，不对外泄露收入。

## 重试与可证明性

前端对同一 SKU、数量和来源组合复用订单幂等键；模拟支付重试复用支付流水标识。服务端仍以订单唯一约束、状态机和支付幂等判断为最终保障。当前自动化验证覆盖商品卡缓存命中后的新鲜性、作者统计越权拒绝、全量 Go 测试、OpenAPI 路由同步、前端类型检查与生产构建。

通过本机现有 OrbStack 启动项目 PostgreSQL 后，`TOKMALL_RUN_PG_INTEGRATION=1` 的隔离 schema 测试已验证：并发挂载上限、幂等挂载、失效后取消、按页商品卡查询、商品下架后卡片保留并标明状态、已支付订单归因仍保留、购买人数去重。Playwright `e2e/commerce.spec.ts` 已跑通作者创建商品与库存、上传并发布视频、挂商品、买家从商品卡下单支付、作者查看 GMV 的完整链路。
