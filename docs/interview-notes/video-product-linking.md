# 视频挂商品：受控推广关系与并发上限

## 1. 解决的业务问题

TokMall 原来已经有视频、商品和订单来源字段，但缺少可信的“视频可以推广哪些商品”写入口。阶段 3A 新增独立 `promotion` 模块，提供：

- 当前用户给视频挂商品，重复请求更新排序或重新启用原关系；
- 调整 `sort_order`；
- 取消挂载时改为 `DISABLED`，保留关系和历史归因；
- 公开查询视频当前可展示的基础商品卡；
- 每个视频最多 5 个 `ACTIVE` 商品，并在真实并发下保证不突破。

订单创建仍会重新校验 `video_id + author_id + product_id + ACTIVE` 的完整来源关系。因此前端展示不是交易授权，下单也不会信任客户端传来的归因字段。

## 2. 为什么单独建立 promotion 模块

`video_products` 表连接内容域和商品域，但它表达的是“推广关系”，既不是商品归属，也不是订单事实。把它塞进 `video`、`product` 或 `order` 任一模块都会让边界变模糊。

因此 promotion 使用自己的 model、repository、service 和 handler。它通过直接 SQL 读取视频和商品的最小事实，不导入相邻模块 model；order 即使读取同一张表也保留自己的 read model。这符合模块化单体未来按边界拆服务的方向。

## 3. v1 权限简化，以及为什么必须诚实说明

长期业务中，作者不等于商家：作者应通过选品广场、商家邀请或推广授权带其他商家的商品。

当前项目还没有平台招商、推广目录和授权关系。如果现在允许作者任意挂全站商品，就等于跳过商品方授权；如果声称“作者永远就是商家”，又会把错误业务模型固化进系统。

所以 v1 采取安全的临时收口：只有当前用户同时满足以下条件才能写关系：

1. 视频属于自己且已经 `PUBLISHED`；
2. 商品属于自己且为 `ON_SALE`；
3. 关系写入的 `author_id` 只取认证上下文，绝不相信请求体。

不存在、越权、未发布、非自有和非在售统一返回 404，不帮助调用者枚举资源。未来引入 `promotion_catalog` / `promotion_authorizations` 后，只替换资格判断，不改变推广关系和订单归因模型。

## 4. 核心不变量

- `(video_id, product_id)` 永远只有一条关系；
- `author_id` 由服务端从认证身份与视频归属推导；
- 每个视频最多 5 条 `ACTIVE` 关系；
- 取消挂载保留为 `DISABLED`，再次挂载复用并重新启用；
- 公开商品卡只展示 `PUBLISHED` 视频、`ACTIVE` 关系、`ON_SALE` 商品以及 `ACTIVE` SKU；
- 商品卡不暴露库存，订单下单时仍重新读取商品与库存事实。

## 5. 并发为什么不能用“先 count 再 insert”

如果两个请求都先查询当前有 4 个商品，它们都可能判断“还没满”，随后各自插入，最终变成 6 个。单纯在 Service 中检查无法阻止这种写偏差，脚本直写也能绕过。

本实现把最终约束放进 PostgreSQL 触发器：

1. 对 `video_id` 计算 advisory transaction lock，同一视频的 ACTIVE 计数与写入串行；
2. 锁粒度是单视频，不影响其他视频并发挂载；
3. 触发器统计已有 ACTIVE 关系，第 6 条抛出具名 CHECK 异常；
4. repository 将该约束错误翻译为领域错误，HTTP 返回 409；
5. 事务提交后锁自动释放，不需要应用自行解锁。

一个容易漏掉的细节是 `INSERT ... ON CONFLICT DO UPDATE` 会先执行 INSERT trigger，再判断唯一键冲突。视频已经满 5 个时，若请求重放的是已有 ACTIVE 关系，触发器必须先识别它并放行，否则正确的幂等更新会被误判成第 6 个。对应场景已写入真实 PostgreSQL 测试。

## 6. 重试、部分失败和锁行为

挂载事务先使用 `FOR SHARE` 锁住视频和商品资格事实，再 UPSERT 推广关系。这样在事务期间，其他事务不能把已校验的视频或商品并发改成不可用状态。资格校验或关系写入任一步失败，整个事务回滚。

重复挂载同一 `(video_id, product_id)` 不新增行，而是更新排序、恢复 `ACTIVE` 并刷新 `updated_at`。取消操作将状态写为 `DISABLED`；重复取消仍得到同一最终状态，不删除历史来源。即使商品之后下架或视频被屏蔽，原作者仍能取消旧挂载；这一命令只检查视频归属和关系归属，不重新要求商品在售或视频已发布。

## 7. 公开读模型为什么不带库存和封面 key

库存是交易域事实，Feed 不应依赖库存表或展示精确库存。基础卡只返回商品 ID、标题、ACTIVE SKU 最低价和排序；没有可售 SKU 的商品不进入结果。

数据库保存的 `cover_key` 也不应直接暴露。阶段 3B 会在 Feed/视频详情按页批量读取关系，再通过 storage 边界批量装配短时效展示 URL，避免 N+1。3A 先把关系正确性与稳定 API 做实，不提前耦合展示装配。

## 8. 测试证据

- Handler：认证身份不可由请求体伪造，参数校验和 404/409 错误映射；
- Service：命令参数、领域错误透传、空列表稳定返回 `[]`；
- Migration 静态检查：触发器、advisory lock、具名约束均存在；
- 真实 PostgreSQL：20 个不同商品并发挂载时恰好 5 个成功，最终 ACTIVE 数为 5；
- 真实 PostgreSQL：20 个相同商品并发挂载最终只有 1 条关系；
- 真实 PostgreSQL：已满视频重放已有关系仍成功；越权、未发布、非自有和非在售均不产生关系。

## 9. 当前边界与未来演进

- 当前“作者必须也是商品商家”仅是缺少推广授权体系时的安全 v1，不是长期业务定义；
- 当前上限 5 写在数据库函数和公开契约中，未来若需配置化，应由平台配置表或约束版本统一管理，不能只改应用常量；
- 3B 将完成 Feed 按页批量商品卡装配和封面签名；
- 后续引入推广授权后，可支持一个作者带多个商家的货，以及一个商品被多个作者推广；
- 成交统计应基于订单支付事实异步聚合，而不是扫描当前仍 ACTIVE 的推广关系，因为关系可能在成交后被停用。
