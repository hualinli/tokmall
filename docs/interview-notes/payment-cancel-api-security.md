# 支付 / 取消 API 的安全边界

## 这一步解决了什么问题

阶段 2A 已经实现订单支付、取消的事务和竞争控制，但还没有 HTTP 入口。直接把 `Pay` 方法包装成“支付回调”会制造一个严重的假象：任何人只要知道订单号，就能伪造渠道通知并把订单改成已支付。

当前项目没有接入真实支付渠道，也没有渠道公钥、签名算法、通知时间窗和证书轮换能力。因此本阶段只暴露两个受 JWT 保护的用户命令：

- `POST /api/v1/orders/{id}/pay`：学习环境模拟当前用户支付；
- `POST /api/v1/orders/{id}/cancel`：当前用户主动取消订单。

它们不是支付渠道回调。OpenAPI 和代码注释都明确记录了这个边界，避免面试时把模拟能力包装成真实支付接入。

## 为什么身份只能从认证上下文获取

请求体不接受 `user_id`。Handler 只读取认证中间件写入的当前用户 ID，并把它与路径中的订单 ID 一起传给 Service。Repository 加锁读取订单时使用：

```sql
WHERE id = ? AND user_id = ?
FOR UPDATE
```

这不是只在 Handler 做一次“查完再判断”，而是把所有权放进真正参与状态迁移的锁定条件。这样可以保证：

1. 调用者不能通过伪造请求体身份支付或取消他人订单；
2. 不存在订单和非本人订单都返回 `ORDER_NOT_FOUND`，避免订单 ID 枚举；
3. 越权支付在查询阶段就结束，不会创建 payment，也不会修改订单状态。

真实 PostgreSQL 集成测试会验证第三点，而不只验证 HTTP 状态码。

## API 与领域错误怎样对应

支付和取消都使用 `200 OK` 返回首次成功或幂等重放，并通过 `replayed` 表明是否复用了既有结果。调用方重试时无需针对不同成功状态码写分支。

冲突类错误保持可区分：

- `PAYMENT_AMOUNT_MISMATCH`：请求金额与服务端订单金额不一致；
- `ORDER_STATE_CONFLICT`：订单已处于不能迁移的终态，例如已取消订单收到晚到支付；
- `IDEMPOTENCY_CONFLICT`：相同支付号或渠道交易号指向了不同支付事实；
- `ORDER_NOT_FOUND`：订单不存在或不属于当前用户，统一 404。

这些错误都返回 409 或 404，但业务码不同。HTTP 状态表达大类，业务码让客户端和排障日志知道究竟是哪条不变量被拒绝。

## 并发、重试和部分失败会怎样

支付与取消仍复用阶段 2A 的事务边界和订单行锁：

- 支付与取消同时到达时，会串行锁定同一订单；只有一个能从 `PENDING_PAYMENT` 迁移到终态；
- 取消成功时，订单状态、库存回补、库存流水在同一事务提交；
- 相同支付事实重复到达只返回原 payment，不重复写入；
- 同一取消请求重放只返回已取消订单，不重复回补；
- 数据库事务失败会整体回滚，不留下“订单已取消但库存没回来”或“payment 成功但订单未支付”的半状态。

## 为什么模拟支付仍保留金额和两个支付标识

虽然这不是渠道回调，仍保留 `payment_no`、`provider_trade_no` 和 `amount`，因为它们能在本地演示真实支付确认最重要的三个问题：本系统支付尝试幂等、渠道交易幂等、服务端金额校验。

这些字段由客户端提交只适用于学习环境。真实系统中，`payment_no` 通常由支付域生成，渠道交易号和金额来自验签后的渠道通知；不能直接信任浏览器传值。

## 为什么现在不实现真实回调

“有一个 callback URL”不等于接入支付。真实回调至少需要：

- 验证渠道签名和证书链；
- 校验商户号、应用号、订单号、币种和金额；
- 限制通知时间窗并防重放；
- 保存可审计的渠道通知摘要；
- 支持渠道查询补偿、证书轮换和密钥托管。

项目目前没有具体渠道协议，虚构一个通用签名字段只会形成不可证明的安全设计。因此真实回调被明确留为独立适配器边界：未来由渠道 Adapter 完成验签与规范化，再调用内部支付确认命令；用户模拟端点不能复用为公网回调。

## 面试表达

可以这样概括：

> 我没有把内部 `Pay` 方法直接暴露成伪支付回调，因为没有渠道验签时那相当于公开改订单状态。当前只做受 JWT 保护的用户模拟支付，身份来自认证上下文，并在数据库锁定条件中同时校验订单 ID 和用户 ID；非本人订单统一 404。支付金额不一致、订单状态冲突和支付幂等冲突使用不同业务码。真实支付回调未来会放在独立渠道适配层，验签、防重放和商户金额校验通过后，才进入同一个领域状态机。
