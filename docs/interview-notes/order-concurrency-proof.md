# 创建订单 API 与防超卖并发证明

## 这一步交付了什么

阶段 1C 把此前只存在于领域层的创建订单能力接到了受保护 HTTP 端点：

```text
POST /api/v1/orders
```

第一版只支持单 SKU。请求包含 `sku_id`、`quantity`、`idempotency_key`，以及可选但必须完整提供的
`source(video_id, author_id, product_id)`。`user_id` 不允许由客户端提交，只从认证中间件写入的上下文读取，
避免用户替别人下单或抢占别人的幂等键。

HTTP 请求/响应 DTO 与 service DTO 分开定义。这样 API 字段、校验标签和序列化格式不会渗透到领域层，
持久化 model 也不会被 Handler 直接序列化。首次创建和同载荷幂等重放都返回 `201` 和相同响应结构，
响应中的 `replayed` 只用于观测和调试，客户端重试不需要切换解析逻辑。

## 核心事务与不变量

创建订单在一个 PostgreSQL 事务中完成：

1. 读取在售商品和启用 SKU，并取服务端价格；
2. 按 `(user_id, idempotency_key)` 创建订单幂等 claim；
3. 执行 `UPDATE inventory SET quantity = quantity - ? WHERE sku_id = ? AND quantity >= ?`；
4. 写入 `ORDER_CREATED` 库存流水；
5. 写入订单项和商品快照；
6. 全部成功才提交，任一步失败都整体回滚。

核心不变量是：库存永不为负；一个成功订单恰好有一个订单项和一条负向库存流水；相同用户、相同幂等键、
相同请求只能形成一份订单事实；相同键复用到不同载荷必须冲突。

这里没有使用“先查库存，再在应用内减库存”。那种写法的两个请求可能同时看到库存充足并各自扣减。
条件更新把“检查余额”和“扣减”合并为一条 SQL；PostgreSQL 在更新同一库存行时获取行级排他锁，竞争请求按数据库
锁顺序重新判断 `quantity >= requested`，库存耗尽后 `RowsAffected == 0`，因此不会超卖。

## 单元测试能证明什么，不能证明什么

普通 `go test` 覆盖：

- Handler 不接收客户端 `user_id`，只使用认证上下文；
- HTTP DTO 到 service DTO 的映射与稳定响应格式；
- 参数非法、不可售/来源无效、库存不足、幂等冲突和未知错误的统一映射；
- OpenAPI 与运行时路由双向同步；
- fake repository 下的指纹、用户级幂等和重复请求语义。

这些测试快速、确定，适合每次提交运行，但 fake 无法证明 PostgreSQL 的锁、唯一约束和事务回滚在真实并发下成立。
因此本阶段另加了显式开启的真实数据库实验。

## 真实 PostgreSQL 并发实验

运行方式：

```bash
TOKMALL_RUN_PG_INTEGRATION=1 \
TOKMALL_TEST_DATABASE_DSN='host=127.0.0.1 user=tokmall password=tokmall dbname=tokmall port=5432 sslmode=disable' \
go test ./internal/order -run TestPostgresOrderConcurrencyProof -count=1 -v
```

测试不会在普通 `go test` 中连接数据库。显式开启后，它会在目标测试库创建随机命名的独立 schema，按顺序执行全部
历史 up migration，实验结束后关闭连接并 `DROP SCHEMA ... CASCADE`，不复用或清理开发业务表。

第一组实验准备 100 件库存，启动 500 个 goroutine，以 500 个不同用户和不同幂等键同时购买 1 件，并断言：

- 恰好 100 个成功；
- 恰好 400 个返回库存不足；
- 最终库存为 0；
- 订单数和订单项数都是 100；
- `ORDER_CREATED` 流水数为 100，变更合计为 -100；
- 不存在缺少订单项或库存流水的半订单。

第二组实验让同一用户用同一个 key 并发重试 100 次，断言所有调用拿到同一订单，只创建 1 个订单和订单项、
只扣 1 件库存、只写 1 条流水。2026-09-16 在项目标准 PostgreSQL 5432 环境中，两组实验均通过。

## 为什么流水和余额都要检查

只验证库存不为负还不够。某个错误实现可能把库存扣对了，却漏写订单项或流水；也可能订单成功但流水重复。
库存余额回答“现在还剩多少”，订单项回答“卖出了什么”，流水回答“为什么发生这次变化”。并发实验同时校验三者，
后续才能用 `期初库存 + 流水变更合计 = 当前库存` 做对账，并定位补偿或人工调整造成的差异。

## 当前性能边界与后续演进

这个实验是正确性实验，不是吞吐基准。500 个 goroutine 会受测试连接池上限约束，而同一 SKU 的库存行本来就是热点，
其更新最终在该行锁上串行化。当前普通商城流量下，这种数据库条件扣减简单、可靠、容易审计，应优先使用。

如果后续压测证明热点 SKU 行锁已经成为可测量瓶颈，再考虑入口限流、排队、Redis Lua 预扣和异步下单；这些方案会引入
缓存与数据库双写、失败补偿、消息可靠性和对账成本，不能只为了在简历上出现“秒杀”而提前引入。

阶段 2 还会补支付、取消和超时关单竞争，以及库存只回补一次。届时流水将继续作为状态竞争和补偿正确性的审计证据。
