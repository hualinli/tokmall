# 面试问题清单（30 题）

用来理解自己的项目、练习项目面试。答案只写要点，细节点进链接看正文。

**答题顺序：** 现在怎么做 → 为什么 → 哪段代码或实验能证明 → 还有什么限制。能脱稿说清并接住一个追问，再勾选。报性能数字时，同时说出场景、并发、时长、错误率和对账结果。

| 轮次 | 题目 | 目标 |
|---|---|---|
| 一：核心链路 | Q01～Q10 | 能演示一次交易，画出下单事务和 Feed 请求 |
| 二：取舍与边界 | Q11～Q19 | 能说清每个设计的代价和不能承诺的部分 |
| 三：故障与恢复 | Q20～Q23 | 能讲最近的真实缺陷：现象、证据、修复、限制 |
| 四：压测 | Q24～Q26 | 能读一份报告，解释数字的适用范围 |
| 五：审视自己的设计 | Q27～Q30 | 能主动指出设计缺口和待证明的技术选择 |

## 一：核心链路

### Q01. 一分钟介绍项目

- [ ] 从使用场景讲起，再选两个工程亮点。

作者发布视频并挂自己的商品，买家从商品卡下单，完成模拟支付、发货、确认或全额退款。后端重点是并发交易、Feed 缓存分页、异步事件与对账恢复。追问"支付是真的吗"：不是，是模拟命令；券后端完整，但网页还没接。证据：[业务](business.md)。

### Q02. PG、Redis、RustFS 各做什么？为什么是模块化单体？

- [ ] 能画出前端、API、三种依赖、后台任务的关系。

PG 存全部事实，Redis 做缓存、限流、热榜和事件传输，RustFS 存媒体。共享 PG 让订单、库存、券、Outbox 在一个本地事务里提交。拆服务会把这些不变量变成跨服务一致性问题，而现在没有需要拆分的理由。证据：[总体结构](architecture.md#monolith)。

### Q03. 最后一件库存被两人同时买，怎么防超卖？

- [ ] 写出条件扣减，说出事务里还有哪些写入。

`UPDATE ... SET quantity = quantity - ? WHERE quantity >= ?`，按影响行数判断，另有非负 CHECK。订单、明细、流水、券、超时事件同事务，库存放在最后，缩短热点行的持锁时间。"先查再减"有竞态。证据：[下单事务](architecture.md#下单事务)、[500 人抢 100 件测试](../internal/order/postgres_integration_test.go)、[库存不足全回滚测试](../internal/order/create_rollback_integration_test.go)。

### Q04. 双击或超时重试，如何只生成一单？

- [ ] 区分"同键同载荷"、"同键异载荷"和"不同键"。

幂等范围是 `(user_id, idempotency_key)`，指纹包含 SKU、数量、来源、券。事务开头取 advisory lock 再查原单，唯一约束兜底。为什么不先锁券：同键重试会先撞上"券已被首单占用"而失败。证据：[同键同券并发测试](../internal/order/coupon_postgres_integration_test.go)。

### Q05. 支付、取消、发货、退款并发时状态怎么守住？

- [ ] 画出状态图，区分履约命令和完整状态图。

订单行锁 + `WHERE status = from` + 流水唯一键。履约用独立的迁移表：如果复用完整状态图，"退款被拒后恢复原状态"那条边会被误当成发货许可。证据：[履约与退款](architecture.md#履约与退款)、[退款竞争测试](../internal/order/refund_postgres_integration_test.go)。

### Q06. 一次 Feed 请求经过哪些步骤？缓存命中为什么还查库？

- [ ] 从路由讲到响应。

handler 解析参数 → service 校验游标，从缓存或仓储拿视频页 → 复制共享结果 → 一条 SQL 合并读点赞和商品卡 → 签发 URL 返回。视频主体可以缓存，点赞和价格要保持新鲜。点赞和 SKU 先分别聚合再 JOIN，否则计数会被乘大。证据：[dynamic_read.go](../internal/feed/dynamic_read.go)、[新鲜度测试](../internal/feed/dynamic_read_integration_test.go)。

### Q07. 为什么用游标分页？同一时间发布的视频怎么办？

- [ ] 讲清排序键、limit+1、签名。

按 `(published_at, id)` 倒序，id 打破平局；游标是上一页末项，取 limit+1 条判断 has_more；HMAC 防篡改，Base64 只是编码。游标提供稳定边界，但不冻结全站内容。证据：[cursor.go](../internal/feed/cursor.go)。

### Q08. Cache-Aside、singleflight、L1/L2 各解决什么？

- [ ] 说清失效流程和"为什么只是最终一致"。

Cache-Aside 在 miss 时回源回填，singleflight 合并进程内的并发回源，L1 减少 Redis 访问，L2 让多个实例共享。写后先删 L1、再删 L2、递增版本号；全局首页的回填按版本条件写入。删除失败、版本读取失败、探测间隔都会留下陈旧窗口，所以是最终一致。singleflight 不能跨进程合并。证据：[缓存](architecture.md#cache)。

### Q09. 支付提交后进程崩溃，统计怎么办？为什么用 Outbox？

- [ ] 指出"提交事实"和"发送消息"之间的故障窗口。

支付事实和事件在同一个 PG 事务写入，中继随后发送。如果在事务里直接发 Redis，PG 回滚撤销不了已发出的消息，两边没有共同事务。发送成功、标记前崩溃会重发，所以投递是至少一次。证据：[事件](architecture.md#events)。

### Q10. 同一消息收到两次，怎么不重复累计？什么时候 ACK？

- [ ] 讲清回执、投影、提交、XACK 的顺序。

回执和投影同一事务提交，提交后才 XACK。回执冲突说明已处理过；提交后、ACK 前崩溃会再收到一次，但不会再累计。不能人工删回执再重放。证据：[consumer.go](../internal/outbox/consumer.go)。

## 二：取舍与边界

### Q11. 三层怎么分工，错误怎么传？

handler 做 DTO 和错误映射，service 做规则，repository 做 SQL 并翻译 ORM 错误。包装用 `%w`，判断用 `errors.Is/As`，业务拒绝不打 Error 日志。一个真实教训：账号 status 的零值绕过了 DB 默认值，导致注册后无法登录。证据：[注册登录 PG 测试](../internal/user/postgres_integration_test.go)。

### Q12. 支付时发现订单已过期，为什么不能在事务里直接返回错误？

关单的副作用（EXPIRED、回补库存、退券）必须提交；在事务闭包里返回错误会把它们一起回滚。所以先提交，再在事务外返回"已过期"。三条关单路径由行锁、状态条件和流水唯一键保证只生效一次。证据：[支付与超时](architecture.md#order-expiry)。

### Q13. 券怎么防超发、防重复用、退款后还能再用？

领券锁模板行，条件递增发行量，检查限领；下单锁持券行再条件核销。退券后订单仍保留券引用作为历史，部分唯一索引只约束仍占券的订单。证据：[优惠券](architecture.md#优惠券)、[000024](../migrations/000024_closed_order_coupon.up.sql)。

### Q14. 热榜怎么保证翻页稳定？Redis 坏了怎么办？

分钟桶加上冻结窗口；游标包含窗口、分数、ID，窗口过期就拒绝游标。首页遇到故障可以降级为时间流，之后继续用时间游标；已经在翻热榜的请求直接报错，不中途换排序。追问"被删的视频怎么办"：跳过它，游标按扫描边界推进，所以一页可能不满。证据：[热榜](architecture.md#热榜)。

### Q15. 关注流是推还是拉？为什么不每个作者取最近 5 条？

拉模式，读完整时间线：0 关注直接返回，1～32 个作者逐作者归并，更多时走全局索引。每个作者固定取 TOP5 会永久丢掉更旧的作品。推拉混合的难点在于：新关注回填、取消关注过滤、策略切换时不漏项。证据：[时间流](architecture.md#时间流与游标)。

### Q16. 大量不存在的 ID 怎么挡？布隆过滤器有用吗？

挡住穿透的是负缓存：只记录真实的 DB miss，不记录"不可见"；Redis 故障时放行。布隆过滤器已经删除，因为它的本地阴性证明不了其他实例没刚创建这条记录，却要占内存并全表重建。证据：[存在性判定](architecture.md#existence)。

### Q17. 为什么上传到 staging 再复制？为什么还要异步校验？

签名绑定长度和类型，封存时检查实际大小，并按 ETag 条件复制，防止检查后对象被替换。对象存在不代表能播放，ffprobe 判定 PASSED/REJECTED；工具缺失记 SKIPPED，不能说成已验证。复制成功但 PG 回滚会留下孤儿对象。证据：[媒体](architecture.md#media)。

### Q18. JWT 怎么续期和撤销？限流的 key 怎么取？

refresh 按 jti 用 Redis `SET NX` 抢占，防止并发重复签发。access 不逐请求检查撤销。限流读按 IP、写按用户，认证另按"规范化账号的哈希"计数；默认不信任转发头。localStorage 防不了 XSS。证据：[认证](architecture.md#auth)。

### Q19. 视频带货的成交来源可信吗？毛额怎么算？

来源由客户端提交，服务端只校验推广关系存在，不能证明真实点击，所以不能用来结算佣金。毛额包含后来退款的订单，退款额单列，日销按 UTC 自然日归集。证据：[成交统计](business.md#成交统计)。

## 三：故障与恢复

### Q20. 讲一次你定位的复杂问题：消费组 pending=0，为什么还缺事件？

- [ ] 两分钟讲完：现象 → 假设 → 证据 → 修复 → 限制。

现象：压测后对账发现上万个事件缺回执，Redis 却显示 pending=0、lag=0。按 PG event_id 追踪成功 XADD 的 Stream ID，发现缺失的消息全部早于保留边界，而且不在 DLQ 里，于是怀疑 `MAXLEN ~ 10000` 裁掉了未消费的消息。把上限调大，全部闭环，证实了根因。正式修复改为按确认水位裁剪，容量满时背压。限制：消费能力不足时积压仍会增长。证据：[诊断](../benchmarks/2026-10-11/diagnosis/README.md)、[保留测试](../internal/outbox/retention_integration_test.go)。

### Q21. "投影可以从事实重建"为什么还会让 GMV 翻倍？

支付已提交但事件还没消费时重建：投影先计入 200，旧事件随后到达，因为没有回执又加 200。现在的门禁是：指定消费组、支付/退款回执齐全、NOWAIT 表锁，任一不满足就拒绝。只停消费者是不够的。证据：[对账与恢复](architecture.md#recovery)、[门禁测试](../internal/reconcile/rebuild_integration_test.go)。

### Q22. 消费者一直在跑，PEL 尾部的消息为什么恢复不到？

原来每次 XAUTOCLAIM 都从头扫，前面大量未超时的消息挡住了后面已超时的。现在用分页 XPENDING 保存扫描位置，空页也继续推进，到末尾绕回；投递次数查询失败就不认领，否则毒丸会逃过 DLQ 阈值。证据：[分页恢复测试](../internal/outbox/claim_pagination_test.go)。

### Q23. 为什么连接池分成 20+5，而不是扩到 50？

热点订单等锁时仍占着连接，前台耗尽共享池，消费者拿不到连接，积压越来越大。预算隔离保证消费者一定有连接；扩大连接数只会把排队搬进 PG。实验结果：热点场景的消费收敛从 31.9 秒降到 1.0 秒，但 HTTP 吞吐没有提升。证据：[步骤 2](../benchmarks/2026-10-12/step2-consumer-budget/README.md)。

## 四：压测

### Q24. 怎么设计一次可信的压测？

专用库、编译好的二进制、记录版本和环境；同机同版本只改一个变量，三轮交错，报中位数和范围；交易必须对账通过才算成功。固定并发是闭环模型，证明不了积压能收敛，需要再补固定到达率实验。证据：[读数规则](performance.md#读数规则)。

### Q25. ORM 藏起了 SQL，压测现场怎么查锁？EXPLAIN 很快为什么接口仍慢？

用 `pg_stat_activity` 加 `pg_blocking_pids` 实时采样，再结合连接池 WaitCount 和 block profile 里的 `DB.conn`，串成证据链："等锁占连接 → 池排队 → 消费者被挤压"。EXPLAIN 不包含取连接的排队时间。证据：[锁等待](performance.md#lock-waits)、[profile](performance.md#profiles)。

### Q26. 简历上的"+43%"和"25.2 万单"具体是什么？

43%：Feed 首页，同连接预算、100 并发、60 秒×3，合并动态查询后吞吐中位数 6,484 → 9,270 请求/秒，零错误；只适用于热缓存、稀疏数据。25.2 万：库存临界区优化后六轮交易的总单数，全部通过对账，证明的是正确性，不是容量。优化前只有单轮参考，不能说成严格 A/B。证据：[最近结果](performance.md#latest-results)。

## 五：审视自己的设计

### Q27. 买家一直不点确认收货会怎样？为什么自动确认不用延迟事件？

原来订单会一直停在 FULFILLING，买家一直保留全额退款权。现在发货时写入截止时间，由轮询 worker 用 `SKIP LOCKED` 批量确认；与退款申请竞争时，谁先提交谁生效。不用延迟事件，是因为退款被拒后截止时间要顺延，已发出的事件撤不回，而且分钟级精度轮询就够了。退款处理时限也按同样的原因用轮询，但每笔单独事务并复用同意退款。还没补的是"仅退款"和"退货退款"的区分。证据：[履约与退款](architecture.md#履约与退款)、[PG 测试](../internal/order/auto_complete_postgres_integration_test.go)。

### Q28. 为什么用 Redis Streams，而不是让消费者直接从 PG outbox 表取？

单进程、PG 本身就是事实源时，Streams 多出一个队列。最难的几个 bug（裁剪丢消息、PEL 尾部、DEAD 与 DLQ 分两处）都来自这个额外的队列。500 条空事件的排空对照里，Streams 三次都略快（大约 0.8–0.9 秒，直接消费大约 0.9–1.1 秒），所以还不能凭耗时删掉它，也不能把它说成已经证明有必要。默认仍走 Redis。`OUTBOX_TRANSPORT=postgres` 留给还没做的固定到达率实验。证据：[排空对照](performance.md#streams-vs-postgres)。

### Q29. 布隆过滤器不参与判定，为什么还留着？

已经删了。修复跨实例假阴性之后，阴性结果也必须继续查负缓存和数据库，它就只剩成本：内存加上每 10 分钟的全表重建。留下负缓存，因为它确实能把确认过的 miss 挡在数据库外面。能主动说出"删掉了什么"，比硬讲"用布隆防穿透"更可信。

### Q30. 再给两周你做什么？为什么不上微服务？

先补业务闭环（前端用券），再做 Streams 对照和固定到达率实验，用数据决定删掉什么、保留什么。拆服务解决不了库存热点和消费不足，反而增加跨服务一致性成本。证据：[roadmap](roadmap.md)。

## 容易失分的说法

| 不要说 | 更准确的说法 |
|---|---|
| 布隆过滤器挡住了不存在的 ID | 布隆过滤器已删除；挡住穿透的是负缓存 |
| 事务保证了支付和发消息一起成功 | 事实与 Outbox 同事务，投递至少一次，消费幂等 |
| 删了缓存就是强一致 | 有失效失败、版本读取失败和探测间隔，是最终一致 |
| pending=0 说明处理完了 | 还要看 PG 待投递事件、回执和投影 |
| 25.2 万单证明可以上生产 | 这是限定条件的本机实验，证明的是正确性 |
| 用 Kafka 就能解决积压 | 消费端的 DB 瓶颈不会因为换 broker 而消失 |
