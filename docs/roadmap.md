## 后端边界，按实际需求决定

| 边界 | 现状 | 进入条件 / 验收 |
|---|---|---|
| 对象存储配额与孤儿回收 | 单次大小已绑定签名并封存校验；没有用户每日/累计配额。复制成功而 DB 回滚可留下无引用最终对象 | 公开部署或存储成本成为问题时，定义预留/核销/释放，防并发超额；回收不能删仍引用或正在封存的对象 |
| 锁内对象存储调用 | 票证封存、媒体回写与业务行锁串行，封存有超时 | 先测慢 RustFS 对连接池/锁等待的影响；有可测瓶颈再考虑封存状态、租约和补偿流程 |
| 账户停用语义 | 登录/refresh 检查可用性；access JWT 的验证未逐请求查账户，公开资料过滤也需统一 | 明确是否要求即时禁止访问、历史内容是否仍公开，再补一致策略与测试 |
| 来源归因与商家授权 | 当前按 owner ID 授权，不要求 MERCHANT 角色；下单来源由客户端提交，只校验活动推广关系，不复查视频发布状态或证明点击 | 保持个人创作者即商家的当前语义；需要角色隔离/结算时定义权限与可信归因，不直接把现有统计当佣金依据 |
| 缓存新鲜度 | 全局 L1 有版本探测；关注首页仍依赖用户失效和 TTL，发布/删除不会遍历全部粉丝 key | 当前 L2 DEL 失败会跳过 Bump，版本读取失败也沿用旧值；用确定性测试和双实例实验核对陈旧窗口；强可见性要求出现时再增加版本或读时过滤 |
| 真实资金与物流 | 买家模拟支付、商家裁决模拟全额退款、模拟发货；COMPLETED 不接受退款 | 接真实渠道时独立验签入口、渠道幂等/重试/对账；部分退款/退货入库单独定义资金与库存模型 |
| 服务化和消息系统 | 同库模块化单体 + Redis Streams；Kafka、Feed inbox fanout、异步点赞/播放未接入 | 团队/容量/跨机房需求明确且测量证明有收益，才引入跨服务补偿与新 broker |
| 生产运维 | 有本地 compose、规则与看板、traceparent；无完整 OTel exporter、Alertmanager 通知配置和 CD 流水线 | 按排障/SLO需要接通知/追踪，补备份恢复、发布回滚与密钥管理；先验证多实例，不必先拆服务 |

## 前端接入单独计数

优惠券后端（发券/领取/订单核销/退券/对账）、热榜后端和媒体校验均已实现。前端尚未接领券/选券/发券界面、`/feed/hot` 入口，也没有完整表达媒体 PENDING/PASSED/REJECTED/SKIPPED 的状态；这些是接入缺口，不能把后端能力写成未实现。

## 演进顺序与停止规则

先收尾与补证据，再选择真实问题：热点 SKU 行锁受限才试 Redis 预扣/排队；关注拉模式受限才试推拉混合；稳定卡片或统计查询成为瓶颈才拆缓存层。每次只验证一个主要变量，交付代码、故障测试、同条件 A/B 数据和更新后的 ADR。没有触发条件时，不为了增加技术名词开启秒杀、购物车、佣金、Agent 客服或微服务。
