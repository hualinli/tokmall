# 路线图

这里只列尚未完成的工作和进入条件，已完成的内容不在这里重复。

## 优先：业务闭环

| 工作 | 现状 | 验收 |
|---|---|---|
| 已发货退款类型 | 已发货退款不退货也不回补库存 | 区分"仅退款"与"退货退款"，后者在退货入库后再回补 |
| 前端优惠券 | 后端完整，网页没有发券、领券、选券 | 网页能完成"发券 → 领券 → 用券下单 → 退款退券" |
| 前端热榜、商品管理 | `/feed/hot`、上下架、搜索都没有调用 | 有页面入口，E2E 覆盖 |
| 日销投影的读者 | `author_sales_daily` 没有接口读取 | 按 [性能计划](performance.md#plan) 的实验结果，决定统计接口改读投影，还是删除投影 |

## 技术清理

| 工作 | 现状 | 验收 |
|---|---|---|
| 消费者参数装配 | 配置已解析 `OUTBOX_CLAIM_IDLE` / `OUTBOX_CONSUMER_MAX_DELIVERIES`，`main.go` 没有传给消费者 | 装配后验证环境变量覆盖生效，默认值不变 |
| 订单超时双机制 | 延迟事件和 5 秒轮询做同一件事 | 用实验决定保留哪一个 |
| 清理任务告警 | `object_delete_jobs` 没有积压告警 | 监控待处理数、失败数、最老任务年龄 |
| 演练脚本 | `make drill` 用随机媒体；`drill-failure` 部分步骤只观察、不制造故障 | 真实媒体与模拟模式分开；每段故障有真实触发和断言 |
| 迁移回滚 | 没有完整 up/down 流水线 | 空库启动、旧数据升级、回滚条件可复现 |
| 死链接 | `migrations/000019` 的注释指向已删除的文档 | 下次改该区域时顺手清理 |

## 补证据

按 [性能计划](performance.md#plan) 逐项完成。500 条事件的排空对照已经做了，见 [Streams 与直接消费](performance.md#streams-vs-postgres)。还没做的是固定到达率 300 单/秒、30 分钟，用它决定默认传输要不要改。

每次只验证一个主要变量，保存原始数据，同步更新对应文档。

## 按需求触发

| 方向 | 进入条件 |
|---|---|
| Redis 预扣 / 排队下单 | 固定到达率实验确认热点库存行是瓶颈，且入口保护、缩短事务都不够 |
| 关注流推拉混合 | 关注规模和读写比例的测量证明拉模式受限 |
| 批量消费 / 多消费者 | 持续负载下消费积压不收敛 |
| 对象存储配额与孤儿回收 | 公开部署或存储成本成为问题；回收不能删除仍被引用或正在封存的对象 |
| 账户即时停用 | 明确要求时，在 access token 校验时检查账户状态，并补对应测试 |
| HttpOnly Cookie + CSRF | 需要更强的浏览器凭据保护 |
| 可信归因与结算 | 需要按归因分佣时，先定义可信点击来源和商家授权 |
| 真实支付与物流 | 独立的验签回调、渠道幂等、主动查单、渠道对账；部分退款和退货入库另行设计资金与库存模型 |
| 微服务 / Kafka | 出现独立部署、团队边界或跨机房需求，且测量证明有收益 |
| 生产运维 | Alertmanager 通知、OTel 导出、备份恢复、CD 与密钥管理；先验证多实例部署 |

没有触发条件时，不为了增加技术名词去做秒杀、购物车、佣金、微服务。
